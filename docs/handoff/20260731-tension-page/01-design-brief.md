## 1. 這個頁面在做什麼

三層聚合的分析管線，每層都要人審核：

```
TEU（場景級）  →  TensionLine（跨場景）  →  TensionTheme（全書級）
   38 個              6 條                     1 句命題
```

- **TEU**：單一場景裡的一組對立極（極點 A vs 極點 B、強度、原文引證、載體實體）
- **TensionLine**：把相關 TEU 聚成一條反覆出現的張力軸，**使用者要逐條核准／改標籤／拒絕**
- **TensionTheme**：從已審核的線合成一句全書命題 + Frye／Booker 框架分類，**也要審核**

使用者是**閱讀分析者**，不是一般讀者。這個頁面的價值在於「我能不能相信這份分析」，所以**可稽核性 > 美觀**。

## 2. 核心診斷：3 步 stepper vs 5 階段工作流

這是使用者親口回報的問題，也是本次重新設計的主軸。

現在的 stepper 呈現：

```
[1] TEU 組裝  →  [2] TensionLine 聚合  →  [3] TensionTheme 合成
```

實際的工作流：

```
[1] 組裝 → 〔檢視 38 個 TEU〕 → [2] 聚合 → 〔逐條審核 6 條線〕 → [3] 合成
              ↑ 完全不存在                      ↑ 不在 stepper 裡
```

使用者的原話：

> 「按完第一個好像看不到什麼東西就要按第二組……整體操作起來順序感會很怪異」

三顆按鈕橫排、每顆都有 CTA 箭頭，視覺上是一組連續動作；但正確用法是在 2 和 3 之間插入可能長達數十分鐘的人工審核。**審核必須成為進度模型裡的一等公民。**

## 3. 真實資料的形狀（設計約束）

以下每一條都經過實測，不是推測。

### 3.1 多數張力線只涵蓋單一章節

```
range=[1,7]  實際有 TEU 的章=[1,5,7]   6 TEU  0.72
range=[3,3]  實際=[3]                  3 TEU  0.73
range=[4,4]  實際=[4]                  3 TEU  0.80
range=[8,8]  實際=[8]                  4 TEU  0.82
range=[9,9]  實際=[9]                  4 TEU  0.75
range=[7,7]  實際=[7]                  2 TEU  0.85
```

**6 條有 5 條是單章。** 現況把 `chapter_range` 畫成橫向長條，於是 5 條退化成 20px 的樁子，橫軸對 83% 的資料沒有資訊量。

而且 `chapter_range` 是 **`[min, max]` 區間端點，不是章節集合**——那條 `[1,7]` 實際只有 ch1／5／7 有 TEU，現況畫成實心長條，等於謊稱 ch2/3/4/6 也參與。

> 這曾被誤判為聚合的 bug。修正覆蓋率並重跑後，單章仍佔多數，**確認是資料的常態，不是缺陷**。橫向時間軸不是對的隱喻。

### 3.2 約 4 成 TEU 不屬於任何張力線

```
38 個 TEU → 22 個進入張力線，16 個是孤兒（42%）
ch2、ch6、ch10 整章的 TEU 全數落單
```

聚合是單一 LLM 呼叫，模型會自由略過 TEU。被略過的**在現況畫面上完全不存在**——軌跡圖的軸只畫到 Ch9，因為 maxChapter 是從殘存的線推算的，ch10 徹底消失。

孤兒不是雜訊，包含 intensity 0.9 的項目。

**這是設計必須新增的東西：孤兒 TEU 要有容身之處。** 沒有它，使用者永遠不知道自己少了四成分析。API 已備妥（`teus.json` 每筆的 `line_id: null` 即為孤兒）。

### 3.3 極點標籤比想像中長

實測 10–16 個中文字（A + B 合計）。現況標籤欄固定寬度，**6 條有 4 條被截斷**：

```
「記憶的自主與神聖 vs 記憶…」
「追尋與承擔 vs 保護與避免…」
「過去的執念與誘惑 vs 活在…」
```

橫軸沒資訊、縱軸讀不完 → 現況那張圖等於不能用。

### 3.4 強度集中在窄帶

實測 6 條線：0.72 / 0.73 / 0.75 / 0.80 / 0.82 / 0.85。

現況用絕對門檻分三桶（0.4 / 0.75），結果**全部落在同一桶**，三色圖例形同單色。另一組測試資料則全部落在中間桶。LLM 輸出天生集中在 0.7–0.9，**絕對門檻沒有鑑別力**——若要用顏色編碼強度，得用本書分布的相對位置。

### 3.5 「3 則證據」可能是同一場戲數三次

5 條線的所有 TEU 都在單一章節內，而同章的 TEU 常是同一場戲的不同改寫：

```
· 這場景的核心衝突在於記憶的本質：它是否可以被視為一種商品…
· 這場衝突的核心在於記憶的本質：它究竟是不可侵犯的個人領域…
· 這場衝突的核心在於記憶的本質：它究竟是神聖不可侵犯的個人遺產…
```

引文也重複引同樣幾句對白。現況呈現「3 TEU · 73%」「證據 3 則」，審核者會讀成三重佐證。**證據數量的呈現必須誠實。**

### 3.6 極點 A/B 的載體會對調

同一條線內，各 TEU 的 A/B 指派是不穩定的：

```
ch3  A=['泰奧多爾・萬克']  B=['伊內絲']
ch3  A=['伊內絲']          B=['泰奧多爾・萬克']
ch3  A=['伊內絲']          B=['泰奧多爾・萬克']
```

現況跨 TEU 聚合後，極點 A 與極點 B 顯示**完全相同的兩個人**（見 `current-03-line-card.png`）。pills 目前是零資訊且誤導。

這是資料層的不穩定，UI 只能緩解：多數決並標示比例／按 TEU 分別顯示／衝突時不顯示。**這是需要設計判斷的地方。**

## 4. 後端剛備妥、設計可以用的新資訊

以下四項在本次重新設計前不存在，請善加利用：

| 資料 | 來源 | 設計價值 |
|------|------|----------|
| **孤兒標記** | `teus.json` 的 `line_id: null` | 稽核視圖的基礎；也讓 Step 1 有產出可看 |
| **載體實體型別** | `pole_*_carriers[].entity_type` | 現況全部染成「角色」色；實測 120 個載體裡有 16 個地點、7 個物件、6 個概念被畫錯。CSS 早就支援六種型別 |
| **極點 stance** | `pole_*_stance` | 說明「這些載體如何體現該極」，例如「泰奧多爾試圖用金錢換取伊內絲幫助他尋找莉莉安娜的記憶，將記憶視為可以買賣的物品。」**先前完全沒顯示過**，正是審核者判斷極點是否成立所缺的資訊 |
| **主題過期狀態** | `theme.json` 的 `is_stale` / `stale_reason` | 重跑聚合或改變審核後，主題就建立在不再適用的輸入上 |

`entity_type` 約五分之一為 `null`（LLM 指認的載體名對不上 KG 實體），設計不得假設型別必然存在。

## 5. 必須解決的設計問題

依重要性排序。前四項是這次重新設計的理由。

### D1. 讓審核成為進度模型的一部分

Step 2 與 Step 3 之間有一段人工工作，現在完全沒有表達。使用者被誘導一路按到底，而那樣做出來的主題是用**未審核**的線合成的。

需要：審核進度可見（`已審核 3 / 6`）、Step 3 在未審核完時有明確狀態、審核完成後有收束。

### D2. 軌跡圖重做

橫向時間軸對這份資料是錯的隱喻（§3.1）。需要能同時表達：

- 單章線（多數）與少數跨章線
- 跨章線的章節**不連續**
- 每條線在各章的強度起伏（現況只畫幾顆大小幾乎相同的圓點，0.42 與 0.88 的半徑只差 1.8px）
- 8–16 字的極點標籤要讀得完
- 最後一章的內容不能被容器裁掉（現況 ch9 那條線完全在畫布外）

### D3. 孤兒 TEU 要有去處

42% 的分析成果目前無處可見。這同時解決「Step 1 按完看不到東西」——TEU 檢視既是 Step 1 的產出回饋，也是稽核介面。

### D4. 證據要能被查證，且數量要誠實

- 證據引文與章節目前是純文字，**無法回到原文**。審核者要判斷一條線成不成立，只能自己切到閱讀頁翻章節
- 重複的 TEU 要摺疊或標示（§3.5），不要讓「3 則」看起來像三重佐證
- 載體 pills 的 A/B 問題（§3.6）需要設計決定

### D5. 審核清單的規模

現況每條線要 2 次點擊才看得到完整證據（展開卡片 → 展開全部 N 則）。6 條線 = 12 次點擊；曾測到 18 條的情境會變成一面同質卡片牆。

需要：批次操作、鍵盤流程、排序、以及**兩套互相打架的篩選機制合而為一**（現況選「已拒絕 1」+ 勾「隱藏已拒絕」會得到 0 筆，而空狀態叫你去調整錯誤的那個控制項）。

### D6. 空狀態

現況 onboarding hero 已經解釋完三層管線，下面又接一個空狀態，然後半頁空白。而且 Step 1 跑完之後，空狀態仍寫著「請先執行 Step 1 和 Step 2」——叫你去做你剛做完的事。

## 6. 功能盤點（不得遺失）

重新設計可以任意改變形狀，但以下能力必須存在：

**觸發與監看**
- 三個步驟各自可觸發，執行中顯示進度與階段文字
- 已完成的步驟可重新執行（會呼叫 LLM、覆寫結果，**必須二次確認**）
- 各步驟的錯誤訊息

**審核**
- 張力線：核准／改寫極點標籤／拒絕
- 主題：核准／改寫命題／拒絕
- 依審核狀態篩選

**呈現**
- 全書命題 + Frye／Booker 框架分類 + 合成來源與時間
- 每條線：極點、強度、章節範圍、TEU 數、主題註記、審核狀態
- 每個 TEU：章節、強度、衝突描述、原文引證、雙極載體、雙極 stance
- 各章 TEU 密度（**注意**：現況的密度值被 §3.5 的重複 TEU 灌水）

## 7. 技術約束

- **主題系統**：所有顏色／字體一律用 CSS variable（`var(--*)`），禁止硬編碼色碼。token 定義在 `frontend/src/styles/tokens.css`，對照表在 `docs/DESIGN_TOKENS.md`。新增或修改 token 必須同步該對照表
- **既有 token 可用**：`--entity-{char,org,con,loc,obj,other}-*`（載體型別）、`--tension-intensity-{low,mid,high}-*`、`--frye-*`、`--booker-*`、`--color-warning*`
- **深色／淺色主題**：切換邏輯唯一入口是 ThemeContext
- **CSS 入口**：`frontend/src/styles/tension.css`（class prefix `.tn-*`），現況 940 行、**0 個 `@media`**——完全沒有 RWD，1024px 下版面會壞
- **元件入口**：`frontend/src/components/tension/`
- **可重用元件**：`components/ui/` 有 `ConfirmDialog`、`LoadingSpinner`、`ErrorMessage`、`MarkdownRenderer`
- **無障礙**：現況每列有兩個指向同一動作的 tab stop；TEU 圓點只有 `title` tooltip，鍵盤與觸控取用不到
- **規格文件**：`docs/UI_SPEC.md` §3.8 記錄現況；`docs/API_CONTRACT.md` #14 系列為 API 唯一規格

## 8. 給設計的提醒

1. **對著 `sample-payloads/` 的真實 payload 設計，不要用假資料。** 難看的部分正是設計要解決的東西
2. **示範資料只作結構參考**——實作時所有數值一律從真實 API 計算，不寫死
3. **可稽核性優先於美觀。** 這個頁面的使用者在判斷「這份分析可不可信」
4. 資料量參考：一本 10 章的書產出 38 TEU / 6 條線。檢驗清單規模請用
   `sample-payloads/lines-scale-18.json`（構造樣本，18 條），屆時同質卡片會變成一面牆
