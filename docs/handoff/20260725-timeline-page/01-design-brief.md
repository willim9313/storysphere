## 2. 資料事實（設計的基礎，勿臆造）

以 `sample-payloads/timeline.json`（真實 #13a 回應）為準。實測數字：

| 欄位 | 實測分布 | 對設計的意義 |
|------|----------|--------------|
| 事件總數 | **62**，橫跨 Ch.1–7 | 每章 6–11 個，章節帶寬度不均 |
| `title` 長度 | 6–17 字（中位 **12**） | 可用真實字串排版，勿用 lorem |
| `description` 長度 | 33–77 字（中位 56） | 詳情面板概要區 |
| `participants` | 中位 **4**，但**有一筆 24 人** | 卡片顯示 2 + `+N`；詳情面板要能排 24 顆 pill |
| 不重複角色 | **67 位** | 篩選面板的角色 chip 會有 67 顆（現有搜尋框） |
| `location` | **0 / 62（全空）** | ⚠️ 地點維度在真實資料中不存在；篩選的「地點」分區會整區隱藏 |
| `eventType` | **8 種**：plot 20 / revelation 16 / conflict 12 / meeting 7 / alliance 3 / battle 2 / turning_point 1 / other 1 | 篩選 chip 8 顆，分布極不平均 |
| `eventImportance` | KERNEL 10 / SATELLITE 3 / **null 49** | ⚠️ **八成事件的 K/S 標籤顯示「·」**——這正是 §4.0 要解的問題 |
| EEP 覆蓋率 | **13 / 62（21%）** | 詳情面板多數時候是「未分析」態 |

> ⚠️ 示範 payload 的人名／章號／文字僅為**結構參考**，設計中的排版請照真實字串長度分布，
> 但實作一律即時從真實圖譜計算、**不寫死示範值**。

### 2.1 `chronologicalRank` 的現實：**算完之後仍有 16% 是 null**

`chronological_rank`（0.0→1.0，事件在**故事時間**中的位置）**可以是 `null`**，
代表「該事件排不進故事時序」。這不是例外，是常態：

| | rank 非空 | rank = null |
|---|---|---|
| 跑「重新計算時序」**之前** | 0 / 62（0%） | **62（100%）** |
| 跑「重新計算時序」**之後**（2026-07-25 實跑） | 52 / 62（84%） | **10（16%）** |

**算完了還是有 10 筆排不進去。** 所以「未排序事件」不是一個過渡狀態，
而是**穩定存在的一類**。任何新視圖都必須先設計好它們放哪。
矩陣視圖現有的解法是 degraded row（Y = -0.1）+「⤵ 未排序事件」象限標籤，可沿用該語彙。

`sample-payloads/timeline-computed.json` 就是算完之後的真實回應（52 有 / 10 無）。

### 2.2 ⚠️ 畫面上一條連線都不會有：199 條關係全部被丟棄

實跑後 `temporalRelations` 有 **200 筆**，但：

| 類型 | 筆數 | 現況處理 |
|------|------|----------|
| `before` | **199** | ⚠️ **全部丟棄**——畫布只收 `CAUSES` |
| `unknown` | 1 | 丟棄 |
| `CAUSES` | **0** | 畫布唯一會畫的類型，實際上一筆都沒有 |

也就是說：**現況設計的 CAUSES 連線樣式（實線／虛線、箭頭、confidence 分級）
在真實資料上永遠不會出現，而手上有 199 條沒被使用的時序關係。**

這對設計的意義：不要假設「連線」是稀有的裝飾。若把 `before` 納入呈現，
畫面上會同時有 199 條線（62 個節點），**線的密度管理會是主要的設計問題**。

### 2.3 ⚠️ Genette 的成功態在真實資料上到不了

「Genette 分析」有一道前置門檻：`storyTimeHint`（事件的故事時間線索文字，
如「此時天尚未亮」「卯時中」）覆蓋率需 **≥ 60%**。

實測：**9 / 62（14.5%）**，且跑完時序計算**沒有改善**（兩者資料來源不同）。

因此：
- **S10「Genette 覆蓋率不足」是這頁的常態，不是邊緣狀態**——請把它當主要狀態設計
- **S11（成功 banner + 結構 chip）、S27（displacement 色帶）、S30（矩陣 Genette 著色）
  在真實資料上都到不了**，只能用構造樣本呈現

### 2.4 `narrativeMode` 實際上只有一種值

實測 **62 / 62 全部是 `present`**。倒敘（flashback）／預敘（flashforward）／
並行（parallel）三種樣式與 `ParallelGroup` 群組樣式**在真實資料上都不出現**。

→ 這三者 + §2.3 的 displacement，共同構成 `sample-payloads/timeline-constructed.json`
（**手工構造，明確標示**）的存在理由。設計這些樣式時請用那份，
但**不要以為真實畫面會長那樣**。

### 2.2 兩個名詞的正確語意（文案不得誤用）

- **「故事時序」（fabula）vs「章節順序」（sjuzhet）**：前者是事件實際發生的先後，
  後者是作者敘述的先後。整頁的核心價值就是這兩者的落差。
- **詳情面板的「上下文位置」不是因果、也不是時序**：它的定義是「與本事件**共享參與者**、
  且位於**較早／較晚章節**的事件」。**文案一律不得稱之為「因果」或「前驅／後續」**
  （事件分析頁已於 PR #18 正名，本頁跟進）。

## 4. 設計需求清單

### 4.0 【最高】工具列右半邊：說不清楚自己在幹嘛 ⭐ 本次重點

**使用者原話**：「這邊當初設計上好像沒有寫得很清楚在幹麻。」

```
現況：[⇄ ↕]  [☰ 篩選]  [↻ 重新計算時序]  [⎇ Genette 分析]
```

四個問題：

**(a) ⚠️ 現況的按鈕外觀不是設計決策，是 CSS 意外**
`timeline.css:22` 的 `.tl button`（特異性 0,1,1）蓋掉了 `.tl-btn`（0,1,0）的
`border` 與 `background`。實測 computed：`border: none`、`background: transparent`。
**三顆按鈕靜止時都是裸文字**，底色只在 hover 時出現（`:hover` 特異性夠高才贏回來）。
→ **請直接決定按鈕該長什麼樣，不必揣摩「原本為什麼長這樣」**；開發端負責解特異性衝突。
（這也是為什麼 QualityBanner 的 CTA 看起來像按鈕、工具列這幾顆卻不像。）

**(b) layout 切換零文字**
只有兩個箭頭圖示（`ArrowLeftRight` / `ArrowUpDown`）+ tooltip。而這兩個圖示在多數
產品裡讀起來是「排序／交換」而非「排列方向」。
對比左半邊：三張視圖卡**每張都有一行解釋副標**。同一條工具列，左半在教學、右半零說明。

**(c) 三種性質的操作同一視覺權重**

| 控制項 | 性質 | 代價 | 可逆 |
|--------|------|------|------|
| layout ⇄↕ | 檢視選項 | 免費即時 | ✅ |
| 篩選 | 資料篩選 | 免費即時 | ✅ |
| **重新計算時序** | 觸發 LLM | **數分鐘 + token** | ❌ 覆寫既有 rank |
| **Genette 分析** | 觸發 LLM | **數分鐘 + token** | ❌ |

後兩者的成本只寫在 tooltip，且**沒有確認步驟**。全站慣例是有的：
事件頁與角色頁都用 `ConfirmDialog`，事件頁批次生成還顯示「預估約 7 分鐘 ·
已分析的事件會自動跳過」。**時間軸頁是唯一沒跟上的。**

**(d) 「Genette」是專有名詞，零解釋**
使用者看到一顆灰掉、沒說為什麼灰、也不知道 Genette 是誰的按鈕（S10）。

**要什麼**：分組（檢視選項 / 資料操作 / 昂貴計算）、昂貴操作要有成本感與確認、
停用要在畫面上說明原因、layout 要看得懂、Genette 要有一句人話。

### 4.1 【高】篩選：只能淡化，不能收斂

現況套用篩選只是把不符合的卡片加 `.dim`（變灰），**卡片仍佔位**。
62 張卡、67 位角色的情況下，使用者得在一片灰卡裡目視找亮的。

**要什麼**：
- 「符合 N / 共 M 筆」計數
- 「只顯示符合項」與「淡化其餘」兩種模式（**兩者都有用**：淡化保留上下文與位置感，
  收斂讓長書可讀。請設計切換方式，不要二選一砍掉）
- **S18 篩選結果為空的狀態**（現況未定義）

### 4.1b 【高】橫向畫布：八成的畫面是空白，而且看不出還有內容 ⭐

見 `screenshots/tl-warm-01-narrative.png`。在 1440×900 下：

- **上下各約 300px 全空**。橫向 layout 只有一列章節帶，而
  `.tl-canvas-inner:not(.vertical) { align-items: center }`（UI_SPEC §3.7 的「次軸置中」決策）
  把它垂直置中，內容只佔畫面高度約 **20%**。
- **畫面上只看得到 Ch.1 的 7 張卡**，但實際有 **62 張、scrollWidth 12390px**。
  **沒有任何捲動提示**——使用者不知道右邊還有 55 張卡、還有 6 章。
- 品質 chip「21% 已分析」與旁邊的按鈕一樣是裸文字，分不出哪個可點。

**要什麼**：這片留白要嘛拿來承載導覽（§4.2 的 ruler／minimap 是天然人選），
要嘛改變置中策略。**「內容只佔 20% 高度且看不出還有更多」是本次最該解掉的第一印象問題。**

### 4.2 【高】長書導覽

62 事件橫向排列，畫布 scrollWidth 實測 **12390px**。現況只能靠滑鼠拖。

**要什麼**：章節 ruler 或 minimap、「跳到第 N 章」、鍵盤 `←→` 在事件間移動、
`Esc` 關閉面板、面板開啟時的 focus 落點。

### 4.3 【中】RWD 與詳情面板

現況 `timeline.css` 1304 行只有一個 `@media (max-width: 640px)`。
面板固定 360px、不可摺、不可調寬，在 1280 視窗就把橫向畫布壓得很窄。

**要什麼**：**1440 / 1280 / 1024** 三個寬度下的行為（面板摺疊？覆蓋？可拖曳調寬？）。
**不需處理 < 768px。**

### 4.4 【高】角色軌跡泳道（新視圖）⭐ 新功能

選 1–3 位角色 → 時間軸切成泳道，呈現：誰在哪些事件出現、哪段完全缺席、誰與誰同框。

- **為什麼**：知識圖譜頁看「關係是什麼」，時間軸應該看「關係**何時**發生」。
  現況兩頁的差異只有排版，泳道才是時間軸不可取代的理由。

## 7. 給設計側的已知現象

1. **現況截圖中工具列按鈕沒有邊框與底色是 bug，不是設計**（§4.0a）。
2. **地點維度在真實資料中是空的**（0/62），篩選的地點分區實際上不會出現。
3. **八成事件未分析**（49/62 無 importance），所以卡片上大量顯示「·」而非 K/S。
   工程端會另加「已分析」標記（不需設計），但設計時請假設**多數卡片是資訊稀疏的**。
4. **並行群組、倒敘色帶、CAUSES 連線在種子書中都不出現**——這些樣式請以
   `timeline-constructed.json`（手工構造，已標示）為準，**不要以現況截圖推論它們不存在**。
5. **矩陣視圖的 overplotting**：X 軸是離散章節，同章事件全部疊在同一條垂直線上
   （實測 Ch.2 疊了 11 顆）。現況靠 dot 半徑與 opacity 硬撐，密集章節會糊成一柱。
6. **本書的敘事順序幾乎等於故事順序**：矩陣散點大致貼著 45° 線。
   這頁的核心賣點（sjuzhet 與 fabula 的偏離）在這本書上訊號很弱——
   設計時請確保**「偏離很小」也是一個看得懂的結果**，而不是看起來像沒載入資料。
