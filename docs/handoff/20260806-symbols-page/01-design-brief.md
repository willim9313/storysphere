## 1. 主軸：從「出現幾次」換成「這個意象怎麼行為」

**現況的組織主軸是頻率，而頻率在這份資料上幾乎沒有鑑別度。**

- `名字的潮汐` 29 個意象裡 **17 個只出現 1 次**；最高的「海」13 次
- `大唐雙龍傳` 23 個意象最高只有 **4 次**
- 而且頻率本身不可信：「海」13 次裡有 **5 次來自版權頁與書名頁**（見 §3.1）

象徵的份量本來就跟出現次數無關 ——「懷錶」出現 2 次可能比「手」7 次更關鍵。結果是使用者面對一份 29 個詞、依頻率排序的清單，**沒有任何線索決定該點哪一個**，於是誰都不點。實測詮釋覆蓋率：`名字的潮汐` 1/29、`大唐雙龍傳` 0/23。

### 本輪要達成的轉向

> **清單的每一列要能回答「這個意象在幹嘛」，而不是只給一個數字。**

「在幹嘛」指的是可從既有資料零成本算出的**行為模式** —— 它黏著誰、集中在哪、和哪些意象結盟、什麼時候登場退場（§2 是完整盤點）。這些訊號同時成為排序依據，取代頻率。

### 兩個由此推導的硬約束

1. **這頁必須在零 LLM 成本下就有用。** 覆蓋率 1/29 和 0/23 是這頁的**常態，不是例外**。任何把主要內容鎖在 LLM 詮釋後面的設計都會重現目前的空頁。
2. **LLM 詮釋的角色改變。** 它不再是「這頁唯一的內容」，而是「把已經呈現出來的行為訊號寫成一段論證」。生成入口因此可以是有條件的 —— 當某個意象的行為訊號夠強時才積極邀請使用者花這筆錢。

## 2. 行為訊號盤點（全部零 LLM 成本）

以下訊號全部可從現有 endpoint 算出。設計可自由挑選、組合、命名，不必全用。

| 訊號 | 資料來源 | 實測範例（名字的潮汐） | 注意 |
|------|---------|----------------------|------|
| **角色依附** | SEP `co_occurring_entity_counts` ÷ `frequency` | 「海」13 次裡 6 次與角色**伊內絲**同段（46%） | 必須先做 §3.2 的三重過濾，否則訊號是廢話 |
| **分布形狀** | `chapter_distribution` | 「海」橫跨 ch1–11（6 章有出現）＝貫穿；「泥」集中 ch6–10 ＝後半段；「鹽」只在 ch1–2 ＝開場即退場 | 章節軸不是 `1..N`，見 §3.1 |
| **意象結盟** | `GET /symbols/:id/co-occurrences` | 「海」與 手 4、沙 2、泥 2、光 2 | 與 SEP 的實體清單會重複，見 §3.2 |
| **事件依附** | SEP `co_occurring_event_ids` | 「海」關聯 **25 個事件** | 事件標題需另外解析；目前完全未使用 |
| **登場／退場** | `chapter_distribution` 的首末正文章 | 「鹽」ch2 之後消失；「戒指」只出現在 ch11（結尾才登場） | 中途消失與後段才出現是兩種不同的敘事行為 |
| **證據可信度** | 非正文出現次數 ÷ `frequency` | 「海」5/13 = **38% 的出現來自版權頁** | 高污染度的意象其頻率排名不可信，排序應降權 |

**「值得優先詮釋」的排序應由這些訊號合成，而不是頻率。** 權重未定，見 §8.2。

## 3. 資料現實與陷阱（設計前必讀）

### 3.1 章節座標不是 `1..chapterCount`

出現次數按 chunk 記錄，所以 `chapter_distribution` 的 key 會包含**前置頁（`-1`、`0`）與超出 `book.chapterCount` 的章號**：

```
海 → { "-1": 3, "0": 2, "1": 1, "5": 1, "7": 2, "8": 1, "9": 1, "11": 2 }
```

`-1` / `0` 是書名頁、版權頁、獻詞；`11` 是後記（該書 `chapterCount` 為 10）。**章節清單 API 只回傳 10 個正文章節**，這些章號在閱讀頁沒有對應目標。

實際內容範例 —— 「海」在 `-1` 章的 context 是版權頁全文：

> 「…出版霧港文化事業股份有限公司 書系藍鯨譯叢 037 地址臨**海**市鹽埕區望潮路 118 號…」

它目前排在出現紀錄最前面，也會原封不動進入 SEP 成為 LLM 詮釋的輸入。

### 3.2 共現實體有三個陷阱

`GET /symbols/:id/sep` 是**純資料彙整、無 LLM、已在頁面載入時取用**。「海」的 `co_occurring_entity_counts` 實測（13 次出現）：

| 實體 | `entity_type` | 共現次數 |
|------|--------------|---------|
| 海 | location | **12** |
| 薩爾瑪雷納 | location | 6 |
| 伊內絲 | **character** | 6 |
| 鹽 | concept | 5 |
| 泥灘 | location | 4 |
| 鹽田 | location | 3 |
| 懷錶 | object | 2 |

三個陷阱：

1. **自我匹配**：排名第一的「海」是與意象**同名的 KG 實體**。若直接取 top-1 當訊號，最強的發現永遠是「這個意象總是跟自己一起出現」。**必須依名稱過濾掉意象本身。**
2. **不是角色**：19 個共現實體裡多數是 `location` / `concept` / `object`。現況 UI 把這個 tab 標為「共現角色」—— 即使接上資料，標籤仍是錯的。需依 `entity_type` 分流或改名。
3. **意象與實體重疊**：「鹽」「懷錶」既是這本書的意象，也是 KG 實體。「共現意象」與「共現實體」兩份清單會互相重複，需界定各自語意。

過濾掉自我匹配之後，「海」真正的角色依附訊號是 **伊內絲 6/13（46%）**。

### 3.3 目前 SEP 幾乎沒被使用

現況只拿 `co_occurring_entity_counts` 當一行提示文字。詳情頁的「共現角色 / 共現事件」兩個 tab 吃的是 LLM 詮釋的 `linked_characters` / `linked_events`，所以在沒跑過 LLM 的書上**永遠顯示 0** —— 儘管 19 個實體與 25 個事件早就在手上。

### 3.4 長尾的處理是設計問題

29 個意象裡 17 個只出現 1 次。在行為訊號的框架下，它們幾乎沒有可陳述的行為 —— 只出現一次的詞還不構成象徵。設計需決定它們的位置（見 §8.3）。

## 4. 現況功能盤點（必須全數保留的能力）

可以改呈現方式、改入口位置，不能砍功能。

### 4.1 左側清單（常駐）

| 能力 | 現況入口 | 備註 |
|------|---------|------|
| 類型篩選 | 6 個類型 chip（器物/自然/空間/身體/顏色/其他）+「全部」 | 只顯示該書實際存在的類型 |
| 搜尋 | 搜尋框 | 比對 term 與 aliases |
| 排序 | 頻率 / 首見 / 審核 | 本輪主軸轉向後需重新設計 |
| 意象列 | 型別色點、詞、極性點、別名、密度條、頻率、審核徽章 | 極性點與徽章需已有詮釋才出現 |
| 回總覽 | **只有「全部」chip** | 程式碼自註 "this is the only way back" |

### 4.2 總覽儀表板（未選取任何意象時）

四格統計（意象總數 / 總出現次數 / 已生成詮釋 / 已通過審核）、類型甜甜圈、極性堆疊條、頻率長尾、章節密度熱圖。

### 4.3 意象詳情（選取後）

| 區塊 | 內容 |
|------|------|
| 標題列 | 詞、類型 pill、出現次數、別名 pill |
| 詮釋區 | 三態：未生成 CTA / 生成中（進度＋可取消）/ 詮釋 Hero |
| 詮釋 Hero | 主題命題、敘事極性、模型信心度、佐證綜述、相關角色與事件 chip（可跳頁）、HITL 審核（通過／修訂／駁回）、重新生成 |
| 章節分布 | 長條圖＋峰值標記＋密度圖例 |
| 共現網絡 | 三 tab：共現意象（可點選切換）／共現角色／共現事件 |
| 出現紀錄 | 依章分組、關鍵字與別名高亮、共現詞標籤、跳至閱讀頁 |

## 5. 痛點

### 已於 PR #27 修正（重設計請勿退回舊行為）

| # | 問題 |
|---|------|
| A1 | 三個章節視覺化的軸域寫死 `1..chapterCount`，靜默丟棄前置頁與超界章節（「海」13 次裡 7 次畫不出來） |
| A2 | 卡片寫「首見第 -1 章 · 峰值第 -1 章」，峰值三角形卻在第 7 章；峰值取「前 3 名」而非「達到最大值者」 |
| A3 | 熱圖與密度條各自用該列最大值正規化，導致「海」最淡、只出現 1 次的意象最深 —— 與熱圖存在目的相反 |

### 主軸層級（§1 的轉向直接處理）

1. **排序與呈現以頻率為主軸**，在真實資料上無鑑別度，使用者無從決定該看哪一個。
2. **共現角色／事件恆為 0**，19 個實體與 25 個事件的資料被閒置（§3.3）。
3. **零詮釋狀態下頁面近乎空白** —— 四格統計有兩格恆為 0 且不可點；極性分布卡整張只有一條灰條「未詮釋 · 29」，佔掉半個螢幕寬、資訊量為零。
4. **沒有批次生成**，29 個意象等於 29 次「點進去 → 讀 CTA → 生成 → 等 → 審核」。

### 局部缺陷（重設計順帶處理）

5. **版權頁雜訊被當成最顯眼的象徵證據**（§3.1）。
6. **「跳至閱讀頁」對非正文章節是死路** —— 實測會導到閱讀頁但停在「選擇章節以查看內容」。
7. **每次進頁面打 N 個 404** —— 為了側欄徽章，對每個意象各發一次 interpretation 請求；實測 29 個 = 29 個 404，`limit` 上限 200 → 最壞 200 個請求。屬工程問題，但決定設計能否假設「審核狀態免費可得」（見 §8.4）。
8. **頻率長尾把全部意象畫出來**，其中 17 列是等長的 1 次短棒，無截斷、無收合。
9. **回總覽的唯一出口藏在側欄「全部」chip**，詳情頁標題列沒有麵包屑或返回。
10. **沒有 URL 狀態** —— 選意象、切篩選、切排序網址都不變 → 不能分享、上一頁直接離開整頁。知識圖譜頁翻新已做 F4 深連結，這頁沒跟上。
11. **共現意象只能跳走、不能並看** —— 點共現 pill 會把當前意象換掉，比較脈絡當場消失。

## 6. 技術與資料約束

- **顏色與字體一律用 CSS variable**（`var(--*)`），token 實作在 `frontend/src/styles/tokens.css`；新增或修改 token 必須同步 `docs/DESIGN_TOKENS.md` 的對照表。
- **示範資料只是結構參考。** canvas 裡的人名、章數、座標、prose 一律不得寫死進實作，必須即時從真實資料計算。
- **API response type 一律從 `frontend/src/api/generated.ts` 取用**，不在 `types.ts` 手寫。象徵意象 API 的欄位是 **snake_case**（直接對應 domain model），與 `api/schemas/` 的 camelCase 不同。
- **URL 前綴是 `/symbols/`**，不是 `/books/:bookId/symbols/`。完整規格見 `docs/API_CONTRACT.md` #15a–#15h。
- **LLM 詮釋是付費且非同步的**（`POST /symbols/:id/analyze` → 202 + 專用 polling endpoint）。任何會觸發它的入口都必須是明確的使用者意圖，不能是瀏覽的副作用。
- **色階語意已定案**：熱圖與密度條使用跨意象的單章最大值正規化（PR #27），不要退回 per-row 正規化。
- **章節軸域的共用定義**在 `frontend/src/components/symbols/chapterAxis.ts`（附單元測試），新視覺化請沿用而非重寫。
- **與鄰頁的邊界**：知識圖譜頁回答「誰跟誰有關係」，本頁回答「這個意象承載什麼」。角色依附訊號會踩到前者的地盤，需明確區隔而非重做一個小型圖譜。

## 8. 待決定的開放問題

1. **非正文出現要分區呈現還是預設隱藏可展開？** 版權頁是純雜訊，但獻詞、後記可能有真實象徵意義。要在資料層先過濾，還是全部交給呈現層？
2. **§2 的行為訊號要如何合成排序？** 六個訊號都免費可得，但沒有既定權重。固定啟發式即可，還是要讓使用者切換主軸（例如「依角色依附排」／「依貫穿度排」）？
3. **只出現 1 次的意象（29 個裡的 17 個）擺哪裡？** 收合、降級為「證據不足」、還是照常列出？在行為訊號的框架下它們幾乎沒有可陳述的內容。
4. **§5.7（N 個 404）要在這輪一併處理嗎？** 工程問題，但決定設計能否假設「每個意象的審核狀態免費可得」。
5. **批次生成的規模上限？** 29 個全跑的成本與時間是否可接受，還是預設只給訊號最強的前 N 名？
