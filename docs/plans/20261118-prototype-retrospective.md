## 一、產品概念與資料模型

這一組最根本。原型照規格做完之後，使用者實際操作才發現概念對不上。

### 1. 筆記到底是「一個結論」還是「一堆證據」

- **現象**：
  - 從結果卡存成筆記時，會引用該 run 所有第 2 層以上的證據，結論由使用者另外寫，view 不存進筆記。EV1 存成筆記會掛 431 筆細碎引用，原本那張因果圖反而不見。
  - 筆記頁沒有連回原本的結果卡。
  - Agent 存的筆記同樣不保存圖。（T28、11/17 使用者測試）
- **根因**：01 §5 的筆記只有 `title`、`conclusion`、`methodology_run_id`、`methodology_trace`、`question` 五個欄位；05 沒有筆記頁的線框；設計稿的筆記頁也沒畫 view。這是照規格做出來的結果，不是漏做。
- **可行的補法與代價**：可以從 trace 或 `methodology_run_id` 把 view 重畫回來，但畫出來的是「用現在的資料畫」，不是存檔當下的樣子。要保存當下，得在筆記裡存 view 快照，這會改到資料模型。
- **v4 要決定**：
  - 筆記的主體是什麼？
  - 要不要保存分析結果本身（view 或快照）？
  - 引用要放「整個 run」還是「每一筆證據」？
  - 筆記和產生它的結果之間要怎麼連？

### 2. 「結果卡＝一個 run」與「每個主體一個 run 的方法」不相容

- **現象**：CH2（每個角色一個 run）、CH5（角色×章，60 個 run）、MY4（每個真相一個 run，37 個）都受到影響。
  - 卡片狀態取最新一筆 run。最後一筆剛好不適用時，整張卡顯示「不適用」，後來改成「任一完成就算完成」。（MY4，11/17）
  - 卡片的 `runId` 只指向一個 run：MY4 卡打開只看得到一個真相的判定，CH5 的矩陣有 5 個角色、證據列表卻只有 1 筆。（T28）
  - view 為了畫出全部角色，改成取整本的同類證據，不再看 run。（T22）
  - MCP 的 `get_run(method_id)` 只回最新一個 run，skill 只好改教大腦用 `search_evidence`。（T20、T25）
  - 自動存的筆記只涵蓋一個主體，例如 CH5 那篇只有「瓊斯到第 12 章」。（11/17）
  - N-04d「同 scopeKey 重跑」：引擎吃的是主體 id，`per_character_chapter` 的單一章沒辦法還原。（T13）
- **v4 要決定**：「一次分析」的單位是什麼（一個 run？一組 run？一個 job？），以及卡片、view、筆記、MCP 各要指向哪一個。

### 3. 方法論與 agent 筆記的「重跑」定義

- **現象**：
  - 規格要求另存方法論（N-07e）與 agent 筆記重跑（N-06d `mcp`）都只重放 trace 裡的 `run_method`。可是實測的兩種大腦都直接取用現成結果（`get_run`、`search_evidence`），從來不呼叫 `run_method`；這本來就是設計要的「不重跑、不花 token」。照規格做，另存方法論幾乎都是空的，agent 筆記重跑也沒有東西可以重放。（T27、T28）
  - 使用者選 A（照規格，按鈕多半停用），理由是：「怕偏離計劃太遠，之後回過頭來重新開發問題很大，我現在只想快點看到 prototype 但不想留下一堆不知道為何這樣做的決策」。
  - agent 筆記的重跑最後完全沒做：T23 延後之後一直沒排回任務，所以 T28 條件 3 不通過。
  - 原型沒有方法論執行器。存下來的使用者方法論是 `implemented=false`，存了也不能跑；TM3、MY2 的上游補跑同樣走不通。（T13、T27）
- **v4 要決定**：方法論記的是「這一輪重跑了什麼」，還是「這個結果用到了哪些方法」（從引用的證據回推）？契約 v2 的目的是「換本書也能重跑」，後者比較符合。另外，方法論執行器是不是核心功能？

### 4. 對話是累積的，「一輪一個結果」不順手

- **現象**：使用者會先要結論、再要圖。系統一輪一個結果，筆記在結果 A、圖在結果 B，兩個湊不到一起。只有 view、沒有草稿的結果不能存。「請大腦整理成筆記」只是再叫一次 LLM、開新的一輪，草稿仍然不會併進有圖的那張卡。（11/17）
- **相關**：
  - 已結束的對話不能接著問，因為 Gateway 不支援恢復 session。
  - 同一輪先出 view、後出草稿時，卡片不更新（已修）。
- **v4 要決定**：「結果」的邊界是一輪、一個主題，還是使用者自己挑？草稿能不能跨輪組合？

### 5. 缺「讀者」這個主體

- **現象**：
  - CH5 只算角色，沒有讀者，所以 F5（讀者與華生同步知情）兩次驗收都無法判定。
  - 01 外殼有 `known_by.reader` 欄位，但沒有方法會填它。
  - CH5 只看角色有沒有親身參與事件，被別人轉述而得知的（瑪麗第 4 章）算不出來；private 事件事後被告知，也不會變成已知。（T15、T28）
- **v4 要決定**：讀者知情要不要做成正式的分析主體？「得知」要不要成為一種可抽取的事件或證據？

### 6. 「段落」其實是約 1,200 字的區塊

- **現象**：
  - 沿用的 chunker 把整章接起來，再切成約 1,200 字的塊，四簽名整本只有 70 塊。引文定位的單位是塊，benchmark「段落與英文版一對一」的對應因此遺失。
  - 每章第一塊開頭帶章名，引文偏移包含章名。
  - 抽取單位因此變成 35 個，比估計的 25–30 多，S1 要 70 次呼叫。
  - 使用者當時決定先不改。（T07、T08）
- **v4 要決定**：保留原文段落，或維持 chunk？這會影響引文精細度、單位切法與呼叫數。

### 7. 第 1 層證據之間的關係與寫入規則

- **現象**：
  - **互指要回填**：`hidden_truth.reveal_id` 和 `reveal.hidden_truth_id` 互指，只能先寫一邊，再直接 UPDATE 回填另一邊，等於繞過唯一寫入路徑 `write_evidence`。（T12）
  - **推理屬性寫不進去**：S4 抽出了角色的 `mystery_role`、動機、機會，但寫入層只能新建證據，不能替 S2 已寫好的角色補擴充欄位，所以只留在原始輸出裡。（T12）
  - **揭曉被丟**：`reveal.revealer_id` 必填，可是敘述者直接向讀者揭曉時沒有角色可填。舊書因此丟了 33 筆揭曉，新書丟了 25 筆。（T12、T28）
  - **兩欄沒有資料來源**：`case_type`、`victim_ids` 兩份 prompt 都沒要求輸出，一律寫成 `other` 和空清單。（T12）
  - **層級不一致**：沒有因果連結的孤立事件，其 `event_role` 是第 2 層，其餘是第 3 層，因為層級由 `derived_from` 算出。（T14）
  - **去重靠 hack**：去重時借用 `derived_from` 欄位暫存 key。（T12）
- **v4 要決定**：
  - 第 1 層之間的連結要不要用 `evidence_link` 表達？
  - 要不要允許對既有證據附加擴充欄位？
  - 哪些欄位可以是空的？
  - 層級要由連結推得，還是由方法宣告？

### 8. 筆記規則與題材切片的衝突

- **現象**：
  - 筆記不能引用第 1 層。推理題在沒有 MY4 的時候，草稿大多只能引用第 1 層的線索，於是帶著 `note_cites_level1` 存不了。（T25）
  - 筆記結論的文字裡可能有大腦抄錯的 id；它不在引用清單裡，但會原樣留在筆記文字中。（T25）

### 9. Registry 的表達力不夠

- **宣告寫不出來、只能靠程式擋的**：數量門檻（「事件少於 5 個」）、NS1 的「沒有 kernel 事件」、方法論的前提條件與 config、`genre_ext` 和 `requires.source` 的執行語意。（T05、T13）
- **宣告漏了**：
  - CH4 沒宣告讀 `character`，讀不到角色名稱和種類，群體與動物也被當成角色放進圖。名稱只能用 regex 從證據摘要的固定格式拆出來，格式一變就失效。（T15，待決 #6 至今未決）
  - CH4 的兩種輸入都標成必要，沒有對話的書就不會跑。
- **缺的欄位**：
  - 題材清單：只好寫成 `domain/genres.py` 常數。（T11）
  - 方法名稱和方法說明：結果卡和詳情頁無法照設計稿顯示。（T22、UI 對齊）
  - 機制 id 與中文名稱的對應：靠推測。（T05）
- **自創或草擬、沒人過目的**：選擇器名稱（`events_with_out_degree` 等）是自創的；7 個方法問句是草擬的，一直沒人過目就出現在 UI 上。（T05，待決 #3）
- **v4 要決定**：宣告格式要不要能表達門檻和可選輸入？方法要不要有名稱與說明欄位？

### 10. REST 用 camelCase、MCP 用 snake_case 的轉換成本

- **現象**：
  - REST 的 service 回 camelCase，MCP 要 snake_case，MCP 工具只好直接重讀資料表。
  - MCP 回傳的 args 是 camelCase，前端得兩種拼法都接。
  - 觸發、trace、段落的邏輯原本寫在 route handler 裡，MCP 沒辦法共用，T20 才抽成共用層。（T20、UI 對齊）
- **v4 要決定**：一開始就設計 REST、MCP、UI 共用的查詢層，以及唯一一個命名轉換點。

## 二、入庫品質

T28 驗收的不通過幾乎都出在這裡；方法的問題多半也是從這裡傳下去的。

### 1. 角色合併與名稱解析（S2），影響最大

- **規則太保守**：只認「名字與別名互相對上」。雙胞胎因此沒被誤併，但短名和全名也併不起來，例如「巴塞洛謬」和「巴塞洛謬·肖爾托」、「肖爾托少校」和「約翰·肖爾托少校」。（T10）
- **名字寫法太多**：
  - 英文名：Sherlock Holmes、Major John Sholto、Bartholomew Sholto。
  - 不同譯名：巴塞洛繆、巴塞洛謬。
  - 帶不帶頭銜：瓊斯、瓊斯先生。
  - 描述性的稱呼：木腿男人、邪門的侏儒、小通加。
  - 文本裡沒出現的英文名，整筆角色會被丟掉。
- **別名有雜訊**：代名詞（他、你、我）混進別名。「我」被多個角色宣稱，薩希卜的別名裡還有「我」和「敘述者」。
- **群體多是泛稱**：如「警察」「工人們」「歐洲人」，大多只出現一次。
- **聚焦者解析不到**：S1b 給的名字寫法不一（華生、Watson、我、narrator、華生 (Watson)），S2 對不到角色，就把聚焦者設成空的，看起來像零聚焦。（T10、T28）
- **結果不穩定**：S1 每次的輸出都不同，所以合併結果也跟著變。新書的拆分比舊書更多：華生、撒迪厄斯、巴塞洛謬、少校都被拆開。（T28）
- **往下游擴散**：
  - CH4 裡同一人變成多個節點並自成小陣營，四簽名的四人被拆到兩個陣營。
  - 華生醫生被分進莫斯坦家族。
  - D1 的聚焦統計不準。
- **曾提但被擱置的修法**：「名字只被唯一一個其他角色的名字包含就併入」。使用者當時選先不改。
- **v4 要決定**：
  - 名稱正規化要放在哪一步？
  - 要不要讓 LLM 做全書層級的角色整併？
  - 要不要讓使用者審閱合併結果？

### 2. 事件太細

S1 抽出 411–431 個事件，連續的小動作各自算一個。下游受到的影響：

- EV1 的最長因果鏈有 39 個事件，全落在第 10–12 章，其中的瑣碎事件只因為在鏈上就被判成 kernel。
- kernel 佔 72%。
- EV2 要切成 22 窗。（T14）

**v4 要決定**：事件的粒度，以及是否需要「場景」或「情節段」這一層。

### 3. 訊號標記沒有鑑別力

- **v1**：prompt 寫「七個機制都要判斷」，模型就每個單位把七個全標一遍，七個機制的密度都是 1.00。題材判對靠的是引文和書名，不是密度。（T11）
- **v2**：改 prompt 後密度拉開了，但資訊控制在 35 個單位裡仍然全是 strong，所以 S4 用它挑單位等於全選，省不到呼叫。
- **新書驗收**：混入題材的章節標成全書 1–12 章。（T28 D3）

### 4. 真相的粒度與揭曉連結（S4）

- **真相太粗**：一筆包好幾件事。E1 一筆就包了死因、兇手、手法、進出方式；E2「寶藏沉入河中」被併掉，沒有獨立一筆。
- **有瑣碎的真相**：例如「福爾摩斯用哪種藥」「哈德森太太為何哭」。新書抽出 37 個真相。
- **分批造成揭曉缺漏**：S4b 每批 150 個候選，依序整併，後一批只能看到前一批合併出的真相，所以早批的線索看不到晚出現的真相。舊書因此有 6 個第 12 章的真相沒有任何揭曉。
- **揭曉連錯章**：揭曉多半連到真相「第一次被提到」的那一章，而不是真正揭曉的那一章。新書 E1–E4 的揭曉章都不對。（T28）
- **線索沒指向角色**：毒刺沒有指向任何人，小腳印指向「同夥」而不是通加。舊書有 55 條線索沒有指向任何角色。
- **讀者可見性標錯**：S4 把幾條讀者其實看得到的線索標成看不到，MY4 的判定因此受影響。（MY4）
- **粒度連帶影響判定**：MY4 第一次用「最早揭曉章」算，E1 被判成 unfair；改成「最後一次揭曉」才變成 partially_fair。

### 5. 引文

- LLM 給的引文常會改掉或漏掉標點、刪掉引號中間的「她說，」，或是跨段。照規格嚴格比對只有 87%，加上「忽略標點再比一次」的退路才到 94%。這條退路是規格外的延伸，使用者同意保留。（T10）
- 新書仍有 67 筆因為引文找不到原文而被丟。

### 6. 其他

- **意象分群合併太兇**：門檻 0.75，「刺」一群吸進毒鏢、絞索、竹矛等 15 個詞。
- **枚舉不夠用**：LLM 給了 `relation_state.polarity=mixed`，不在枚舉裡，只能改成 `neutral`。
- **信心是假的**：S1 沒有給信心，一律寫 0.8。
- **文件與書名**：檔頭的譯者說明一度被當成第 1 章（後來修了）；章名沒有「第一章」前綴；書名用的是上傳的檔名。（T07、UI 對齊）

## 三、方法品質

- **EV1**：
  - 分類門檻是實作時自訂的，規格沒寫。
  - 邊界事件交給 LLM 時，問法是「拿掉它，因果鏈會不會斷」，答案幾乎都是會，於是 278 個邊界事件裡約 257 個被判成 kernel。
  - 一個方法就要 278 次呼叫，約佔全書呼叫的六成、費用的四成。
  - 曾建議改成在同一章內做相對比較；使用者說「先提交，之後調」，後來一直沒調。（T14，待決 #9）
- **CH5**：
  - 錯誤認知的品質不穩：有些是猜測語氣，有些連「真相」都說錯（例如說莫斯坦上尉是被少校殺的）。
  - 60 個 run 依序跑，約 8 分鐘。
  - 晚期章節的每筆證據都有幾百條 `derived_from`。（T15）
- **MY4**：
  - 只瞞住角色、讀者本來就知道的真相，問「對讀者公不公平」沒有意義，所以改成跳過。
  - 揭曉章要取最後一次，而不是第一次。
  - 判定結果很依賴 S4 真相的粒度。
  - 真相文字太短時，語言偵測退回英文，LLM 就用英文回答。（MY4）
- **規格、prompt、程式三方對不上**：
  - CH2：03 說要給引文，prompt 卻沒有引文欄位。
  - CH5：prompt 的 meta 寫 secret 和 private，內文卻說只給 secret。
  - EV2：prompt 的輸入列了 participants，但 EV2 只宣告讀 `event`，拿不到角色名字。
  - S3：prompt 要求 LLM 回 `mechanism_density`，程式卻不採用。
  - 方法產出的 `subjects` 角色名稱規格沒有定義，所以都沒有填。（T14、T15、T11）

## 四、大腦（agent）整合

### 安全與隔離（Claude Code 經 ACP）

- **adapter 的預設值不安全**：權限模式是 `auto`、會載入個人的 `~/.claude` 設定、會帶入帳號的連接器。第一次 spike 沒加隔離時，Bash 和 Write 真的寫出了檔案。要擋住，必須同時設 `tools: []`、`settingSources: []`、`strict-mcp-config`，並在建好 session 後切到 `default` 權限模式。（T02）
- **skill 與設定互相牽制**：
  - `tools: []` 時連 skill 都看不到。
  - 改用 `settingSources: ["project"]` 會讀進上層 repo 的 `CLAUDE.md`。
  - session 目錄放在 repo 裡，會帶進本機對這個專案的 auto-memory（`MEMORY.md`）。
  - 最後的做法：session 目錄放系統暫存目錄，skill 經 `plugins` 帶過去。（T26）
- **CLI 內建的 skill（code-review 等）關不掉**：它們沒有工具可用，做不了事，但仍會出現在大腦的清單裡。（T26）
- **模型沒有指定**：實際用的是登入帳號的預設模型（目前是 Opus 5.5），`agent_sessions.model` 是空的，使用者自己設定的模型也不會生效。慢的原因是 Opus 本身較慢、每段新對話都要用 npx 啟動 adapter，再加上每輪多次工具呼叫。（11/18）

### 整合的技術債

- 規格指定的 `langchain-mcp-adapters` 要求 `mcp<2`，和 T20 用的 mcp 2.3 衝突，只好自己寫轉接層。（T25）
- mcp client 的連線不能在不同 task 進出（anyio 限制），改成每個 session 一個常駐 task。
- deepagents 預設會給 `execute`、`write_file` 等工具，要另外寫 middleware 藏起來。
- 大腦同時呼叫多個工具時，`trace_calls.seq` 會重複（已加 lock 修正）。

### 大腦行為

- **skill 的涵蓋範圍決定大腦怎麼做**：原本只有事件和推理兩份 skill，問角色關係時，大腦就讀第 1 層事件自己拼答案；補上角色的 skill 之後才會去拿現成結果。（T25）
  - 過程中我（助理）一度建議把方法清單寫進 system prompt，使用者糾正：skill 本來就是這條路。
- **方法查詢太弱**：`list_methods(query)` 只比對問句的子字串，用「關係」查不到 CH4，大腦又常用英文關鍵字去查中文問句。
- **flash 不照指示**：system prompt 加了提示也不照做，還逐筆讀了 20 筆證據（約 76 秒）。`show_view` 只是建議，所以右側常常沒有結果。
- **長 UUID 抄錯**：flash 抄長 UUID 會錯一碼，造成 `not_found`、`not_in_trace`，結論文字裡也會留下錯的 id。Claude Code 的回覆會引原文，但常常不附證據 id。
- **呼叫數常比估計多**：大腦實測 35–45 次，原本估 15–25 次；MY4 估 8 次，實際 15 次。

**v4 要考慮**：短 id 或代號、更好的方法發現機制、要不要強制呈現結果、skill 怎麼組織。

## 五、成本與可觀測性

- **開發期就在燒錢**：每張任務都拿整本書跑真的 LLM，約 480 次 Gemini 呼叫，費用遠超使用者預期。使用者指出：「以單純開發單元功能而言這是很不智的」。之後的規則是開發一律 mock，整本實跑只在里程碑，而且先報呼叫數。（11/16）
- **subagent 也在花錢**：subagent 開發一樣吃 Claude 額度，每張任務約 10–30 萬 token。期間撞過 5 小時上限、Sonnet 每週上限、Fable 上限，工作多次被中斷。
- **系統不記 token**：`runs.token_usage_json` 從來沒有寫入過，token 和費用只能從帳單反推。方法和 S4b 也沒有保存 LLM 的原始輸出。（11/18）
- **thinking 是費用大頭**：程式沒有設 `thinking_budget`，Gemini 2.5 Flash 預設會動態思考，thinking 約佔費用的 70%。整本中估 455 次呼叫、約 NT$183，若完全不思考約 NT$40。（11/18）
- **花費上限的 429**：撞到 Google 花費上限的預防性限流時，job 會停在 `paused_quota`。伺服器重啟之後不會自動續跑，要手動按續跑。（11/18）
- **進度看不到**：
  - S1 原本省掉了並行，整本要 34 分鐘。（T09）
  - S4b 依序整併 4 批、約 8 分鐘，畫面上的步驟條只寫「執行中」，看起來像卡住。（11/18）
  - 入庫頁的單位格點不開：N-02c（單位原始輸出）的 API 有做，但 T21 的規劃和設計稿都漏了它。（11/18）
- **v4 要考慮**：
  - 每次呼叫記錄 token 與費用。
  - 預算上限與事前估價。
  - 方法類 task 的 thinking 設定。
  - 用 Batch API 跑非即時的工作。
  - EV1 先用規則篩掉明顯的事件再問 LLM。

## 六、工程與架構

- **SQLite 並行**：入庫、SSE 輪詢、API 同時讀寫時會出現 `database is locked`，這也是不穩定測試的根因。改成 WAL 加 30 秒等鎖之後解決，但備份要連 `-wal`、`-shm` 三個檔一起複製。（T19）
- **job 去重只在單一行程有效**：用的是行程內的 asyncio lock。中斷或暫停中的 job 會一直擋住同一個分析，直到續跑或取消。（T13）
- **SSE 是輪詢**：每 0.5 秒比對資料庫狀態再發事件；工作中心沒有全域事件串流，每 2 秒抓一次清單。（T19、T21）
- **dev server 卡住**：`uvicorn --reload` 遇到開著的 SSE 連線會重載不下去，一直佔著 8000 埠。（T23）
- **測試**：
  - 並行測試原本靠 `sleep` 排時序，機器忙時會錯位，其中一處的 `sleep` 甚至寫在 `raise` 之後，沒有作用。（T12–T14）
  - API 測試會讀本機的 `var/settings.yaml`，後來固定成讀預設檔。（T06）
  - 註冊真的方法之後，入庫測試跑到 S5 會去叫真的 LLM，要明確傳一個空的方法引擎。（T14）
  - fixture 不能放 benchmark 的譯文，只能手寫合成資料。
  - 改了 prompt 之後，要手動清掉 S4a 的斷點才會重抽。
- **同一份東西有兩份**：
  - 執行用的 `prompts/` 和 `docs/spec/08_prompts/` 不同步（signal_tagging 一份 v2、一份 v1）。
  - `docs/spec/` 和原稿 `prototype_v0_草案/` 不同步（待決 #5）。
  - 筆記的引用規則一度在 REST 和 MCP 各寫一份。
- **刪書**：上傳的原始檔不會刪；`evidence.book_id` 沒有外鍵。
- **依賴**：
  - `sentence-transformers` 會帶進 torch。
  - Codex 訂閱只有私有、自標 experimental 的類別，所以沒接。
  - npm 官方 registry 曾因 DNS 問題連不上，改從 npmmirror 安裝，再把 lockfile 的網址手動改回官方。
- **CI 從沒跑過**，repo 也沒有遠端。
- **實跑資料的位置**：原本放在暫存目錄，重開機可能消失；使用者要求之後放 `var/benchmark_runs/`。另外，同一份 demo DB 裡有兩本同樣的書。

## 七、UI／UX

- **與設計稿落差很大**（完整原因見桌面那份調查）：
  - 「設計稿不能用瀏覽器開」這個錯誤前提被寫進 README，之後每個 session 都繼承了它，只讀文字、從沒渲染設計稿。
  - 驗收只驗功能，沒有並排比對畫面。
  - 元件庫的規格互相矛盾：05 §2 說用舊 repo 的 kit，設計稿用的是 DS v3 的 kit，缺了 24 個 class，只好用 inline style 拼。
  - 任務之間有縫：設定頁的大腦區塊沒有任何一張任務負責。
  - 節奏太快，大量交給 subagent，合併前沒有做視覺把關。
- **示意資料和真實資料差很多**：設計稿假設大腦的回答很短，實際的回答又長、又帶 markdown 和 id。
- **對話介面不符合主流 chat**：
  - 對話清單沒有標題，只能憑時間猜。
  - 整頁一起捲動，輸入框越推越下面。
  - 工具呼叫全部攤開。
  - 已結束的對話不能接著問。
  - 後來改成左側常駐清單，設計稿同批一起改，以便溯源。
- **大圖看不清**：431 個事件的因果圖，subagent 原本排成一長條，縮成看不清的一團；改成每章一欄之後，仍然要放大才看得到文字。
- **畫面需要但 API 沒有資料的**：
  - 結果卡底部的章節分布色條。
  - 方法名稱與方法說明。
  - 證據「被誰引用」（沒有反查 API）。
  - 「引文未對上原文」的筆數。
- **沒有做的**：
  - 證據審核的「修改」。
  - 拒絕理由用瀏覽器內建的 `window.prompt`。
  - 重跑失敗單位、從某一步重跑、改主題材，以及 `rerunUpstream`，都只有規格、沒有端點也沒有按鈕。
- **很多會改資料或叫 LLM 的按鈕從沒實際按過**：重跑、審核、測試大腦、儲存設定、捨棄、修改後再存、寫入確認卡等。
- **主題切換曾經找不到**：它原本放在首頁，首頁換成書庫後就沒有入口，直到設定頁做好。

## 八、流程與規格管理

- **規格互相矛盾，或和現況對不上**：
  - 第 1 層必須有引文，但角色的輸出沒有 quote 欄位。
  - CH5 要讀 `reveal`，但通用方法不能讀題材的證據。
  - checkpoint 該放獨立檔還是併進 `neo.db`。
  - S5 該另建 job，還是在入庫 job 裡跑。
  - 元件庫該用哪一套。
  - 05 §6 說大腦測試放在啟動測試表，設計稿卻放在大腦卡。
  - 完成標準與任務順序衝突：T25 要驗「線索公平嗎？」，但 MY4 排在後面還沒做，只好換題。
  - 範圍縮減後，05 §1 仍寫「10 張卡」，09 有 6 列已經不適用。
- **規格外的決定大量累積**：各張任務的 subagent 回報裡，型別猜測、門檻、取法往往一次就有 10–30 條。一部分寫回了規格，但很多只留在對話和 STATUS 裡。
- **待決事項長期沒決**：
  - #6：CH4 要不要讀 `character`。
  - #8：S4 三件事。
  - #9：EV1、S2、CH5 說好「之後再調」。
  - #3：7 個草擬問句。
  - 這些到驗收時都還沒決定。
- **人工檢查延後**：使用者說「我能做的測試會落在有畫面可以操作時才算」，所以 T10、T12 的人工檢查都延到有 UI 之後。v4 應該更早提供能看的畫面，或是開發者檢視。
- **subagent 的使用**：
  - 使用者要求派工以節省 context，但 T08 時我（助理）沒照做，也沒先說明。
  - 派出去的工作在合併前只驗功能。
  - subagent 也花額度，而且中途撞上限就停。
- **交接靠 STATUS**：context 一長就開新 session，靠 `STATUS.md` 和交接 prompt 接續。STATUS 長到 62KB，而且有一次 commit 之後才發現忘了寫 STATUS。
- **使用者的原則**：寧可照規格做，也不要留下「不知道為何這樣做」的決策（T27 選 A）。所以 v4 的規格本身要把這些問題先想清楚。
