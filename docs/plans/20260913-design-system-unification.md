# 全站風格統整 — 規劃與現況盤點

> 規劃日期：2026-09-13 · 分支 `design/system-unification-packet`（基於 origin/main `ff51208`）
>
> **這是規劃當下的快照，實作後即凍結。** 與現況衝突時以程式碼、`API_CONTRACT.md`、`UI_SPEC.md` 為準。

## 動機

使用者觀察到「不同功能頁面有密度上的落差」，希望完整截圖全系統畫面，
配合功能說明文件與規格，交給 Claude Design 做一次全頁面風格統整。

## 診斷：問題不在視覺，在三套並存的間距系統

掃描 `frontend/` 全量原始碼後確認，密度落差是機制性的，不是個別頁面的設計失誤。

| 系統 | 尺度 | 用量 | 狀態 |
|------|------|------|------|
| `--space-*` CSS token | 6 階 | 50 | 已定義、已入文件，**實質未採用** |
| CSS 檔內硬寫值 | **43 種**雜值 | 1283 | 事實上的主導系統 |
| Tailwind utility | 原廠尺度 14 階 | 360 | `tailwind.config.ts` 為 `extend: {}`，**未接 token** |

另有 `pages/` 內 240 處 `style={{}}` inline style，改 CSS 與 token 都蓋不到。

**反證**：同一套 token 機制在字級上是成功的（`font-size` token 採用率 90%，649 : 74）。
證明缺的是間距層的規範與強制力，不是要換架構。

完整量測見 packet 內 `00-system/density-audit.md`（由腳本生成，非估算）。

## 關鍵前提：部分密度落差是合理的，不該抹平

`API_CONTRACT.md` 共 100 個 endpoint，各功能區資料厚度差距超過 10 倍
（敘事結構 16、知識圖譜 15、張力 12、象徵 10 ⟷ 章節內容 2、跨書搜尋 1）。
Search 頁與 Symbols 頁承載的資訊量本質不同，強行統一密度會讓前者空洞、後者窒息。

**設計規範要產出的是密度分級，不是單一密度。**

## 交接機制的釐清

Claude Design **不是**「打包寄過去」的外部服務。實際流程：

1. 由我起草 `.dc.html` artboards
2. 發布成 Artifact，內含 Claude Design canvas 編輯器
3. 使用者在 canvas 上視覺微調並 Save
4. 再從該 canvas 實作回程式碼（依既有慣例：實作依據是 canvas，不是散文規格）

因此 packet 的性質是**起草時的工作底稿**，不是交付物。真正的瓶頸是 context window
而非檔案大小，故 packet 按頁面族群分目錄，分批取用。

`DesignSync` 是另一條路（同步元件庫到 claude.ai/design 的 design-system 專案），
本次不用；待 Phase 2 元件統一後可考慮。

## 範圍決策 · 第二輪（2026-09-13 使用者拍板）

前一節的決策定義了「要看多廣」，這一節定義「要收斂成什麼」。依據是 packet 的實測，
不是慣例套用。

### 間距尺度：8 階 `2 / 4 / 6 / 8 / 12 / 16 / 24 / 32`

拿 1679 處實際間距試算各候選尺度的「原地對齊率」（不必改數字的比例）：

| 尺度 | 原地對齊 | 平均位移 |
|------|---------|---------|
| 4 階 `4/8/16/24` | 25.5% | 2.22px |
| 6 階 `2/4/8/12/16/24` | 40.7% | 1.61px |
| **8 階 `2/4/6/8/12/16/24/32`** | **51.3%** | **1.24px** |
| 10 階 `2/4/6/8/10/12/16/20/24/32` | 61.9% | 0.99px |
| 現況 `--space-*` `4/8/16/24/32/48` | 25.9% | 1.87px |

**選 8 階的理由**：對齊率由 26% 提升至 51%，平均位移 1.24px（不可辨識）；
再加到 10 階只多換 10% 對齊率卻多兩個決策點。

**現況 token 失敗的真正原因**：`--space-*` 跳過 6px 與 12px，而這兩個值佔實際用量兩成以上，
所以只能對齊 25.9%。不是開發者不用 token，是那組 token 不合用——這解釋了 3% 的採用率。

另：90% 的間距 ≤16px，故 32px 以上只需一至兩階收尾，不必鋪滿。

**使用者附帶條件**：先踩 8 階，後續重新檢視頁面時可能再調整；階數過多會讓閱讀上
更不一致，故不採 10 階。

### 密度分級：方向二（三級 + 成長預留）

以整頁截圖位元組為資訊量代理指標，跨度 26K–613K（24 倍），三級之間有自然斷層
（60K↔150K、270K↔290K）：

| 分級 | 實測區間 | 頁面 |
|------|---------|------|
| A 工作檯 | 290–613K | 知識圖譜（開面板 613K）、閱讀頁 |
| B 檢視 | 150–270K | 符號、時間軸、事件、角色、張力、建構概覽、搜尋結果 |
| C 入口 | 26–60K | 書庫、上傳、設定、搜尋空態 |

**成長預留**：C 級必須同時定義「滿載版型」。理由是書庫的書會持續增加，
現在的稀疏是暫時狀態，但仍不應與 A/B 級共用同一密度。

### 錯誤態：視覺與行為一併修（範圍擴大至程式邏輯）

現況：10 個路由中 9 個在 API 失敗時退化成完全相同的畫面——一條 Tailwind 寫死的
`ErrorMessage`（`px-4 py-3 gap-3`）橫貼頂端，BookNav 與所有 chrome 消失，
下方約 850px 全白，無重試入口。

使用者決定連行為一起補，需求有三：

1. 統一錯誤版型（置中、留白合理、與空狀態同一套語彙）
2. 補重試入口
3. **區分「這一頁的資料掛了」與「整個後端掛了」** —— 使用者明確表示現況分不清

第 3 項會動到錯誤處理邏輯與 chrome 的保留策略（失敗時仍須保留 BookNav 讓使用者能切走），
**不只是 CSS**。屬 Phase 2 範疇。

### ink 主題產出量減半

使用者比對 warm/ink 截圖後確認版面幾乎相同（與 DESIGN_TOKENS「spacing 與版面不隨主題改變」
一致），ink artboard 由 245 降至約 120，只畫形狀／對比真的改變的狀態。
