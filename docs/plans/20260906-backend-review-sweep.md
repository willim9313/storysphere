## 一、這輪在找什麼

不是找「醜的程式碼」，是找**靜默失效**——不報錯、測試全綠、但實際上沒在做事的東西。

到目前為止命中的每一個，形狀都一樣：**有人寫下了意圖，但沒有任何東西驗證那個意圖仍然成立。**

- `kg_concept` 節點把從未執行的步驟標成「已完成」
- B-048 明文要求「後續缺口都記在這裡」，然後兩個缺口在它眼皮底下長出來沒人記
- `CharacterAnalysisOutput` 被手抄成 dict literal
- `ConceptInferencePipeline` 有兩個活著的消費者，卻從未被呼叫
- 三張標示 ✅ 完成的票（B-024 / B-033 / B-034）都沒填上自己宣告的欄位

## 二、核心判準：零引用 ≠ 死碼

**掃描只能給候選，判定必須逐一走查。** 目前遇到三種結局，比例約為 **12 刪 : 3 接**（前端那批）：

| # | 類型 | 特徵 | 正確處置 |
|---|------|------|---------|
| 1 | **真死碼** | 有明確取代者，或功能已移除 | 刪 |
| 2 | **被手抄的來源** | 有人把它複製成 literal（`CharacterAnalysisOutput` → `analyze_character` 的 dict） | **刪掉會把重複固化**；正解是讓抄的那方改用它 |
| 3 | **未接線的生產者** | 消費端活著但永遠讀到空值（`ConceptInferencePipeline`、`clearMurmur`） | **刪掉會讓缺口永久且隱形**；是產品決定不是清理決定 |

**紅線**：不以「掃描說零引用」為由直接刪除。每一筆都要先判定屬於哪一種。

## 三、工具

`scripts/scan_dead_code.py`（PR #86，四個子命令）

```bash
python scripts/scan_dead_code.py            # 全部
python scripts/scan_dead_code.py backend    # 後端符號（AST）
python scripts/scan_dead_code.py exports    # 前端具名匯出
python scripts/scan_dead_code.py i18n       # i18n key
python scripts/scan_dead_code.py css        # CSS class
```

**偵測器本身就是偽陽性的來源，這是最該記住的一課。** 第一版 i18n 掃描只認
`t(\`ns.x.${v}\`)`，漏掉 `const key = \`ns.x.${v}\`; t(key)`，把三個執行期組出來的 key
判成未用。修法是不看 `t()` 怎麼被呼叫，改成**取所有含插值的模板字面值的靜態前綴**。
CSS 有一模一樣的問題（`` `tl-pill-${type}` ``）。

**掃描器掃不到的東西**（需要另外的探針）：

- **model 欄位** —— `TEU.review_status`、`Entity.source_spans`、`StoryTimeRef.absolute_time`
  都是用「同組手足都有人讀寫、只有它沒有」這個判準手動掃出來的
- 巢狀函式與 class 內部私有方法
- 只被測試引用、生產路徑無呼叫者的符號（**最危險**，測試會讓它看起來活著）
- 已註冊但從未被觸發的執行期物件（例如 chat tool，要看 log 不是讀 code）

## 八、新工作階段怎麼接

1. **先看 PR 狀態**：`gh pr list --state open`。#86 若已合，補 B-093 的條目狀態。
2. **跑一次掃描器取得現況**：`python scripts/scan_dead_code.py`（#86 合併後才有）。
3. **挑一個第六節的區塊**，用這些已證明有效的探針：
   - 這個值域裡的每個值，**結構上**都產得出來嗎？（B-088 的 `processing` 產不出來）
   - 這個欄位有人**寫**嗎？同組手足呢？（`TEU.review_status`、`source_spans`）
   - 這個分支**進得去**嗎？（`tension_service.py:879` 的 `if inferred:` 從未進入）
   - 宣告與現實一致嗎？誰在守？（B-048 的原則沒有機制守）
   - 兩側對稱嗎？（角色 vs 事件，這條命中兩次）
4. **每個發現先判定屬於三種結局的哪一種**，再決定處置。
5. **紀律**：一次 ≤3 檔、五道閘門全綠、產出先給用戶看過再 commit、
   進 main 一律走 PR 且 base main（不堆疊）。

## 九、這輪確立的幾條原則

- **「原則寫在 backlog 但沒有機制守」等於沒有。** B-048 自己就是反例。
  可執行的版本是 PR #83 的作法：把宣告放進**生產程式碼**，用測試釘住宣告等於現實，
  且**雙向**都擋（新增未宣告的、宣告了但已修好的）。
- **哨兵測試要驗自己會紅。** 每個新的漂移防護都實測過改壞情境（B-061 建立的慣例）。
- **不要把「掃描器說的」當成「事實」。** 偵測器的偽陽性已經兩次改變結論。
- **審核關卡設在合成層，不設在原料層。** TEU 是 LLM 從單一場景整理的原料，
  審核要回答的是「這個結論值不值得參考」——那是 TensionLine / TensionTheme 的事。
