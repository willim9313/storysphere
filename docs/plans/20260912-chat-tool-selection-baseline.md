# Chat 工具選擇：ADR-008 的 >85% 第一次被實測

**建立**: 2026-09-12
**狀態**: 規劃快照（依 CLAUDE.md「規劃文件存檔」紀律，存檔後不回頭修改）

> **為什麼要有這一份**：`20260909-post-sweep-development-plan.md` §3-4 問「chat 工具從
> 21 個變 23 個之後，ADR-008 的工具選擇準確率 >85% 目標有沒有受影響」，並註明
> 「這件事只有你能做——要撈 langfuse」。**兩個前提都不成立**：langfuse 從沒開過所以
> 沒有東西可撈，而 chat 走的是 WebSocket、可以直接驅動，不必人工點。
>
> ADR-008 的 85% 原文是「**預估** >85%」（`ADR_008_FULL.md:214`），從未量過。
> 這是第一次。
>
> **plans 不可當作現況**：工具清單與提示措辭以 `tool_registry.py` 與
> `chat_agent_base.py` 為準。

## 一、量測設定

- 語料：《名字的潮汐》(`c4185113`)，`gemini-2.5-flash`，`temperature=0.3`（chat 預設）
- **24 題題庫**，8 組，`docs/` 不收；設計要點是 `expect` 為**可接受集合**而非單一答案
  ——有些問題兩個工具都對，硬指定一個等於在量標註者而不是量 agent
- **每題一個新 session**：同一 session 裡前一題選過的工具會汙染下一題
- A 組 7 題專打工具 description 裡 `DO NOT USE` 畫的那條線（便宜查詢 vs 深度分析）

### 1-1 對題方式：時間窗是錯的，內容才對

**第一次算出 33%，是量測管線自己的錯。** 用「問題的起訖時間」去框 langfuse trace，
窗口一重疊就整串平移一格——每題拿到的是隔壁題的工具。

trace 的 `input` 裡本來就有使用者問句。改用**內容比對**之後是 92%。

這與本輪稍早那個「空迴圈的假綠測試」同類：**量測管線壞掉時，看起來像被測物壞掉**。
判準是先驗證管線能複現已知的東西，再相信它的新結論。

### 1-2 langfuse 的兩個序列化陷阱

- **`role: tool` 的訊息不一定是工具結果。** 一次呼叫的 input 有 24 則 `role:tool`，
  其中 23 則是**工具定義本身**（bound tools 被序列化進訊息串）。只認 assistant 訊息上
  的 `tool_calls`，否則會把 23 個定義數成 23 次呼叫
- **深度工具自己會產 trace。** `analyze_character` 內部另發 5 次 LLM 呼叫（`msgs=2`、
  不帶工具目錄），它們對不上任何題目的問句，要另外歸戶

## 二、結果一：準確率 92%，但 n 撐不住「通過」二字

**22/24 = 92%**（完整 agent，走真實 WebSocket）。

| 組 | | 組 | |
|---|---|---|---|
| A 便宜 vs 深度 | 6/7 | E 比較 | 2/2 |
| B 關係 | 4/4 | F 摘要洞察 | 2/3 |
| C 檢索 | 3/3 | G 圖譜抽取 | 2/2 |
| D 時間軸 | 2/2 | H 事件 | 1/1 |

**兩個失分都是真的，不是標註太嚴：**

| # | 問題 | 選了 | 該選 | 為什麼算錯 |
|---|---|---|---|---|
| 2 | 伊內絲在**哪幾章**出現？ | `get_entity_attributes` | `get_entity_timeline` | 答「第一章首次出現、提及 154 次」，給不出章節清單 |
| 20 | 這本書的主題意涵？ | `get_keywords` | `generate_insight` | 答「從這些關鍵字來看，故事**可能**探討…」，拿關鍵詞猜而非跑洞察 |

**兩個都是選了更便宜的鄰近工具——是「選得不夠積極」，不是過度選擇。**

**n=24 不足以宣告通過。** 22/24 的 95% 信賴區間約 **74%–98%**，**涵蓋 85%**。
成立的說法是「點估計 92%、沒有證據顯示低於門檻」；要把 85% 釘死，n 得往 60 以上走。

## 三、結果二：過度選擇沒有發生

深度工具**被選 2 次、該被選 2 次**，完全吻合。`analyze_character` 只在
「請深入分析…性格、關係與弧線」出現，`analyze_event` 只在「造成什麼後果」出現。
description 裡的 `DO NOT USE` 擋得住。

§3-4 擔心的方向沒有發生；真正發生的是反方向（第二節那兩題）。

---

## 四、結果三：21 vs 23 工具的 A/B —— 逐題完全相同

§3-4 問的是「有沒有**受影響**」，那需要對照組。`analysis_agent=None` → 21 個工具，
給了 → 23 個，開關乾淨。

方法改為**只量選擇這一步**：綁工具、送同一份系統提示（取自真實 trace 的逐字原文）
＋問句，讀回 `tool_calls`，不執行工具。N=3。
**有效性檢查**：23 工具臂用輕量法複現了完整 agent 的逐題結果，方法成立。

| | 全 24 題 | 共同 22 題（不需要深度工具） |
|---|---|---|
| 23 工具 | 22/24 = 92% | **20/22 = 91%** |
| 21 工具 | 21/24 = 88% | **20/22 = 91%** |

**22 題的選擇逐題完全相同，一題都沒變。** N=3 之下三次也全同。

**結論：加那兩個工具對其餘工具的選擇沒有任何影響。** §3-4 的問題可以結案。

## 五、結果四：成本不在深度工具，在工具目錄

§3-4 寫「深度分析工具每次呼叫都跑完整分析，**比其他工具貴得多**」。**不成立。**

| 題 | 工具 | 呼叫 | 秒 | token |
|---|---|---|---|---|
| 15 | `get_global_timeline` | 3 | 13.4 | **34,224** |
| 16 | `get_character_arc` | 4 | 8.9 | **32,546** |
| 4 | ★`analyze_character` | 8 | 16.0 | 32,231 |
| 6 | ★`analyze_event` | 3 | 2.3 | **12,714** |

兩個**普通**工具比 `analyze_character` 還貴；`analyze_event` 與最便宜的無異
（多半吃到快取——所以深度工具的成本是快取狀態的函數，不是固定值）。
要節流該盯的是 `get_global_timeline` 與 `get_character_arc`。

**真正的成本是固定開銷：**

- 每次含目錄的呼叫地板 **4,145 token**，其中約 3,200 是 23 個工具定義、約 900 是系統提示
- 24 題共 48 次含目錄呼叫，**光地板就 198,960 token**，佔全部 input 285,084 的 **70%**
- 含目錄的呼叫佔總 input 的 **95%**

**選哪個工具對成本幾乎沒有影響；有影響的是「每回合把 23 個工具重講一遍」。**

### 5-1 兩條省法

**供應商快取**：系統提示 **97% 穩定**，會變的只有尾巴 84–285 字（頁面脈絡、聚焦實體），
而且**已經在最後面**——形狀對快取有利。但：`gemini-2.5-flash` 的顯式內容快取有最低
token 門檻，4,145 大概不夠格；隱式快取可能適用，然而 **langfuse 的 usage 只給
input/output、沒有 cached token 欄位**，本次無法判斷有沒有命中。要確認得讀原生回應的
`usageMetadata.cachedContentTokenCount`。

**按脈絡裁剪工具目錄**：3,200/4,145 是工具定義。既然選擇本身沒問題，
「閱讀頁不送 `get_relation_stats` / `compare_entities`」這類裁剪能砍同一塊成本，
且不依賴供應商。**未驗證**——裁剪會不會反而降低準確率要另外量。

## 六、結果五：系統提示與工具註冊表是兩份會互相矛盾的真相

21 工具臂的 #6 叫了 `analyze_event`——**那個工具根本沒被提供**。獨立重驗 5/5 全中，
連參數都編得像模像樣（`{"event_id": "泰奧多爾背叛婚約"}`）。

**不是幻覺，是提示在指揮。** 系統提示硬寫了 **16/23 個工具名**當路由規則，其中就有：

```
For "What happened in event X?" ... → get_event_profile ...;
for deep causal/impact analysis → analyze_event
```

而 `get_chat_tools()` 在 `analysis_agent is None` 時把這兩個工具拿掉。**提示說有，
schema 說沒有，模型聽提示的。**

這推翻了 `tool_registry.py:96` 的一句保證：

> The guard stays because the argument is optional: **a caller that has no
> AnalysisAgent still gets a working agent, minus these two.**

拿到的不是「少兩個工具的正常 agent」，是一個會發出 `ToolNode` 解不掉的工具呼叫的 agent。

**目前不是活的 bug**：`deps.py:284` 永遠傳 `analysis_agent`，正式路徑一直是 23 個。
這是**潛伏的**，而且潛伏處正是 B-092/B-104 踩過的同一個坑——工具存在但沒接線。
已開 **B-119**。

## 七、限制

- **單本書、單一模型、題目由實作者自己出**，標註偏誤沒有第二人校過
- **n=24**，信賴區間涵蓋門檻（第二節）
- `generate_insight` 的失分只有 1 筆，不足以說它系統性被忽略
- 成本數字含快取狀態：`analyze_event` 那題便宜多半是快取命中，換一個沒算過的事件
  會不一樣
- **沒量「裁剪工具目錄會不會傷準確率」**，那是第 5-1 節那條路的前提
