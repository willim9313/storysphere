# 10 給 Fable 的驅動 prompt

四段，依序使用。`<SPEC_DIR>` 換成這個資料夾在 Fable 那台機器上的路徑（本機預設 `~/Desktop/storysphere_v4`）。

| # | 什麼時候用 | 用幾次 |
| --- | --- | --- |
| P0 | 開工第一次 | 1 次 |
| P1 | 每做一張任務 | 每張 1 次 |
| P2 | 遇到「人工檢查」的任務做完時 | 7 次（T02、T10、T12、T18、T28 等） |
| P3 | Fable 回報規格衝突或缺口時 | 視需要 |

---

## P0 開工

```
你要開發 StorySphere v4 的 prototype：新版分析契約的後端，加一個檢視成果、可接 agent 大腦的簡易 UI。範圍是通用層＋推理一個題材。

一、取得材料
1. 規格在 <SPEC_DIR>：
   - prototype_v0_草案/（00–10，這次的實作規格）
   - StorySphere分析契約v2/、neo-storysphere-agent-architecture/（上層設計，衝突時以這兩份為準）
   - storysphere_benchmark/（驗證文本；不要複製進 repo）
2. 把舊專案 clone 到旁邊當參考，只讀不改：
   git clone https://github.com/willim9313/storysphere ../storysphere_ref
   規格裡寫「沿用」「改寫自」的模組都在這裡。
3. 新專案建在一個新目錄（例如 ../storysphere_v4_app），git init。

二、先讀，不要寫程式
依序讀 prototype_v0_草案 的 00、01、02、03、05、04、06、07；08、09 做到相關任務時再細讀。
讀完回報：
- 用 5 行以內說明你理解的系統（證據、方法、筆記、大腦各是什麼）。
- 你在規格之間發現的矛盾或看不懂的地方（附檔名與段落）。沒有就寫沒有。

三、建立專案規範
- 把 06_新專案CLAUDE.md 去掉最上面的草案註記，存成新專案根目錄的 CLAUDE.md。之後一律照它做事。
- 把 prototype_v0_草案 整包複製到新專案的 docs/spec/。

四、停下來等我
完成以上後停下。我確認你的理解沒問題，才開始 T01 與 T02。
```

## P1 執行一張任務

```
執行 T{編號}。

1. 讀 docs/spec/07_任務清單.md 的 T{編號}，以及它「依據」欄列出的規格段落。
2. 照 CLAUDE.md 先做 checkpoint：要動哪些檔案、能沿用 ../storysphere_ref 的哪些程式（列到檔名）、有沒有新依賴、怎麼還原。超過 3 個檔案就先拆子步驟。
3. 我同意 checkpoint 後才寫程式。
4. 做完照 CLAUDE.md 的 Definition of Done 回報，並把 T{編號} 的「完成標準」逐條列出：通過／不通過＋證據（測試名稱、指令輸出、run id）。
5. 規格有缺口或互相矛盾時不要自己挑一邊：停下來，用 P3 的格式回報。
6. 這張標了「人工檢查」的話，做完就停，等我看過。
```

如果希望它不必等你同意 checkpoint 就直接做，把第 3 點刪掉；建議至少 M1、M2 保留。

## P2 人工檢查

```
T{編號} 是人工檢查點。請準備給我看的材料，不要往下做：

1. 用四簽名（<SPEC_DIR>/storysphere_benchmark/texts_zh/01_推理_四簽名_柯南道爾_1890_繁中譯.txt）實際跑過這一步。
2. 對照 docs/spec/09_驗收清單.md 的對應小節，逐列標「通過／不通過」，不通過的寫實際結果。
3. 列出你自己覺得可疑、但清單沒涵蓋的結果（最多 10 項）。
4. 告訴我在 UI 或資料庫的哪裡可以自己看（路徑、查詢、畫面）。
5. 這次花了多少 token、多少時間。
```

## P3 規格衝突或缺口

```
回報格式：
- 位置：檔名＋段落（例：01 §6.2、04 N-06c）
- 問題：哪兩處說法不一致，或缺了什麼
- 影響：不決定的話卡住哪張任務
- 選項：最多 3 個，各一行，標出你建議哪個與理由
等我決定後，你先改 docs/spec/ 的對應段落，再改程式。
```
