# 02 入庫流程

把契約 v2「上傳與萃取流程」的 4 步落成可實作的規格。能沿用既有 storysphere 的部分直接沿用，路徑寫在表裡（相對 `backend/storysphere/`）。

## 1. 總覽

```
上傳 ─▶ P1 文件處理 ─▶ [章節審閱 HITL] ─▶ S1 核心抽取＋訊號標記 ─▶ S2 整併
     ─▶ S3 題材判定 ─▶ S4 深度抽取＋整併 ─▶ S5 自動觸發預設分析
```

| 步驟 | 讀什麼 | 寫什麼 | LLM | 沿用既有 |
| --- | --- | --- | --- | --- |
| P1 文件處理 | 檔案 | `books/chapters/paragraphs` | 無 | `pipelines/document_processing/`（loader、chapter_detector、chunker）、`core/language_detection.py` 全部沿用 |
| 章節審閱 | P1 結果 | 章節角色、段落切分修正 | 無 | `workflows/ingestion_graph.py` 的 LangGraph `interrupt()` ＋ SQLite checkpoint，沿用 |
| S1 | 全書正文，**只讀這一次** | 第 1 層核心證據（候選）＋訊號 | 每單位 2 次 | prompt 從 `services/extraction_service.py` 改寫 |
| S2 | S1 候選 | 合併後的第 1 層核心證據 | 意象分群用 embedding，不叫 LLM | `pipelines/knowledge_graph/entity_linker.py`、`paragraph_entity_linker.py`、`services/imagery_extractor.cluster_synonyms` |
| S3 | 訊號分布＋書名＋開頭樣本 | `books.genre_profile` | 1 次 | 新增 |
| S4 | **只讀有訊號的單位** | 題材機制的第 1 層證據 | 每個有訊號單位 1 次＋整併 | 新增 |
| S5 | 證據庫 | 方法產出（第 2 層以上） | 依方法 | 見 03 |

原型決定：有偵測到章節標題時，第一個標題之前的無標題內容（書名頁、譯者說明、譯名表）預設角色為 `other`，不佔章號、不進抽取；審閱時可改回正文。整本書沒有任何標題時不套用。

原型決定：既有 phase 2 的「章節摘要」不做。新契約沒有方法讀它；需要時可在之後加回。

## 2. 抽取單位（window）

既有做法有兩個值得避開的地方：實體抽取逐段呼叫 LLM（呼叫次數多），關係／事件抽取把整章截斷在 8,000 字元（`text[:8000]`，長章後半直接丟掉）。新版改成：

- **單位＝同一章內連續的正文段落**，累積到上限就切。上限依語言：中日韓 3,000 字、其他 8,000 字元（約略同樣的 token 數），可設定。
- **不跨章**：章是敘述位置的基本座標。
- **前文脈絡**：每個單位附上前一單位最後一段，標成 `context_only`，只用來解代名詞，不從中抽取。
- 只處理 `ChapterRole.body` 的章與 `ParagraphRole` 為正文的段落（沿用既有 `extract_body_text`）。
- 每個單位有穩定 id：`{book_id}:{chapter}:{first_paragraph_position}`。
- 原型決定（T08）：
  - 前文脈絡取「全書順序的前一個單位」，章的第一個單位附的是上一章最後一段；全書第一個單位沒有。
  - 單一段落本身超過上限時自成一個單位，不切開段落。
  - 上限目前是 `ingest/units.py` 的常數（`build_units(limit=)` 可覆寫），還沒有設定檔欄位。
  - 單位依序一個一個跑；並行留到 S1（T09）決定。

規模參考：七萬字的中文小說約 25–30 個單位，S1 約 50–60 次呼叫。

## 3. S1 核心抽取＋訊號標記

每個單位同時送兩個呼叫（彼此獨立，可並行，併發數沿用 `settings.ingestion_concurrency`）。

### 呼叫 A：敘事核心（task `core_extraction`）

輸出 JSON：

```json
{
  "characters": [{"name": "", "kind": "person|group", "aliases": [], "description": "", "attributes": {}}],
  "events": [{"title": "", "event_type": "", "description": "", "participants": ["<name>"],
              "significance": null, "consequences": [], "narrative_mode": "", "story_time_hint": null,
              "tension_signal": "", "emotional_intensity": null, "emotional_valence": null,
              "visibility": "", "quote": "<原文片段>"}],
  "relation_states": [{"source": "<name>", "target": "<name>", "relation_type": "", "polarity": "",
                       "weight": 0.0, "is_bidirectional": false, "description": "", "quote": ""}],
  "utterances": [{"speaker": "<name>", "addressees": ["<name>"], "kind": "dialogue|monologue|letter", "quote": ""}]
}
```

- 欄位定義與枚舉沿用既有 `_ENTITY_SYSTEM_PROMPT`、`_RELATION_SYSTEM_PROMPT`（包含「依原文出現順序輸出事件」那條，它決定 `text_rank`）。
- **每筆都要帶 `quote`**，必須是原文逐字片段（S2 會驗證，見 01 §3）。
- 角色以名字指稱；id 在 S2 才指派，所以單位之間不必互相等待。

### 呼叫 B：敘述與訊號（task `signal_tagging`，用便宜模型）

```json
{
  "focalization": {"focalizer": "<name>|null", "type": "zero|internal|external", "person": "first|second|third", "quote": ""},
  "imagery": [{"term": "", "imagery_type": "", "quote": ""}],
  "book_setting_hints": [{"aspect": "", "value": "", "quote": ""}],
  "signals": [{"mechanism": "info_control|world_rules|threat|relations|journey|historicity|language_form",
               "strength": "weak|strong", "subtags": [], "quote": ""}]
}
```

- 七個機制都要判斷，不只看推理。訊號要「寬」：寧可多標 weak，不要漏（契約 v2 風險表「訊號寬鬆、後端嚴格」）。但只輸出這段真的出現的機制，不為了涵蓋而湊數（prompt v2，見 §5 原型決定）。
- 子標籤用各題材契約的詞。推理用到的：資訊控制的 `case`（案件）、`clue`（線索）、`trick`（詭計）。
- 意象的判斷標準沿用既有 `ImageryExtractor` 的 prompt（只收被強調的意象，不收一般形容詞）。

### 共通

- Core prompt 一律英文；描述欄位用書的語言輸出，`quote` 保留原文（既有 CORE.md 多語策略）。
- JSON 解析沿用既有 4 步 fallback（`core/utils/output_extractor.py`）與 `llm_retry`（`core/llm_call.py`）。
- 原始輸出先寫進 `ingest_unit_outputs`，再進 S2。斷線或額度用完時已完成的單位不必重跑（§7）。
- 原型決定（T09）：
  - 呼叫 A＝stage `s1a`、呼叫 B＝stage `s1b`。兩個 stage 同時跑、各自內部依序跑單位（等於同時 2 個呼叫）；`ingestion_concurrency` 設定還沒有。
  - S1 只做「取回文字 → 4 步 JSON 解析 → 檢查最外層的 key 都在」，解析後的物件原樣存進 `raw_json`；欄位驗證與正規化在 S2。解析失敗或缺 key 算一次失敗，照 §7 重試。
  - 不用 provider 的 structured output（訂閱來源與相容端點不一定支援），所以 task 的 `requires: [structured_output]` 對 S1 沒有實際作用。
  - 執行用的 prompt 在 repo 根目錄 `prompts/ingest/`（從 `docs/spec/08_prompts/ingest/` 複製）；之後改 prompt 改的是 `prompts/`，並升 `version`。
  - 沒有前文脈絡時 `context_text` 填 `(none)`。

## 4. S2 整併

依序：

1. **角色合併**：沿用 `EntityLinker`（正規化名稱精確比對、別名交叉比對、提及次數最多者為標準名）。產出 `character` 證據，`first_chapter`／`last_chapter`／`mention_count` 由所有單位彙整。
2. **段落標記**：沿用 `ParagraphEntityLinker`，把角色標到段落與字元偏移；這張表是索引，不是證據。每個角色的**首次提及**（段落與偏移）同時當成該筆 `character` 證據的引文（01 §3）；完全標不到的角色不入庫。
3. **名字換 id**：事件參與者、關係兩端、發話者都換成 `character` 的 evidence id。對不上的名字丟棄該欄位值並記一筆警告，不丟整筆證據。
4. **引文驗證**：每筆 `quote` 對照段落原文（`squash_spacing` 正規化後比對子字串），對上的寫 `evidence_quote` 與偏移，對不上的依 01 §3 處理。
5. **意象分群**：沿用 `cluster_synonyms`（embedding 相似度 0.75），每個群一筆 `imagery_motif`。
6. **書籍背景**：同一 `aspect` 的提示合併成一筆 `book_setting`。
7. **事件順序**：依單位順序與單位內輸出順序指派 `text_rank`。
8. **去重**：依 01 §7。

S2 不叫 LLM，可在本機快速重跑；調整整併規則時不必花 token。

### 原型決定（T10）

實作在 `ingest/s2/`，入口 `run_s2(session_factory, book_id)`；入庫圖在單位節點之後、完成之前跑它。每次執行建一筆 `runs`（`ref_id = ingest.s2`），報告寫在 `summary_json`；重跑時新的一批取代舊的（01 §4）。

**輸入容錯**：`raw_json` 沒驗證過。欄位缺、型別不對的項目丟掉並記警告，不讓整個 S2 失敗。有預設值的選填欄位值不合法時改用預設（例：`polarity` 出現枚舉外的 `mixed` → `neutral`）；必填欄位不合法則丟整筆。

**角色合併**（比既有 `EntityLinker` 保守，寧可拆開不要誤併）：

- 只認「名字 ↔ 別名」的交叉連結；兩組只是共用同一個別名不連結。
- 用來連結的字串至少 2 個字。
- 同一個字串被好幾組當別名、而那些組彼此不相干時，不拿它連結（擋掉「他」「先生」「少校」）。
- 「名字＝另一組的名字＋該組自己的別名」視為同一人（華生醫生＝華生＋醫生）。
- 名字正規化保留 unicode 的字母、數字與組合記號。
- **已知限制**：同一人的短名與全名若沒有別名互指，不會合併。四簽名有兩例：「巴塞洛謬」／「巴塞洛謬·肖爾托」、「肖爾托少校」／「約翰·肖爾托少校」。曾考慮「名字只被唯一一個其他名字包含就合併」，使用者決定先不加（2026-11-16）。
- `mention_count`＝所有單位裡被抽出來的次數總和，不是段落標記標到的次數。
- 別名照 S1 給的存，可能含代名詞（他、你、我）；這些不會被拿去連結或標記。

**段落標記**（比既有 `ParagraphEntityLinker` 保守）：字面至少 2 個字；名字優先於別名；被多個角色宣稱的字面不標；只當別名的字面必須是自己名字的一部分，且不是別人名字的開頭或結尾。標記用段落的完整文字，章名裡的名字也會標到。

**名字換 id**：關係缺任一端、話語缺發話者 → 整筆丟掉。事件參與者、受話者、focalizer 對不上時只丟該值；focalizer 丟掉後該筆看起來會像零聚焦。`evidence_subject.role`：事件 `participant`；關係 `source`／`target`；話語 `speaker`／`addressee`；聚焦 `focalizer`。

**引文**：定位規則見 01 §3「S2 的引文定位」。

**其他**：

- 每個單位的話語最多取 10 筆。
- 聚焦：同章、同 focalizer、同類型、同人稱的相鄰標記併成一筆。
- 意象：只算引文對得上的出現，`frequency` 與 `chapter_distribution` 也只算這些。embedding 模型 `paraphrase-multilingual-MiniLM-L12-v2`（`sentence-transformers`）。0.75 的門檻在四簽名上併得太兇（一群併進十幾個不相干的詞），待調。
- 書籍背景：同一 `aspect` 最常見的說法當 `value`，其餘進 `description`；枚舉外的 `aspect` 併進 `other`。
- 角色不過去重（已由合併規則決定）；其餘類型去重後才指派 `text_rank`。
- `confidence` 一律 0.8（S1 沒給）。

## 5. S3 題材判定（task `genre_detection`）

1. 算每個機制的訊號密度：`有訊號的單位數 ÷ 總單位數`，另算 strong 的比例與分布的章節範圍。
2. 一次 LLM 呼叫，輸入：這張密度表、各機制前 5 個 strong 訊號的引文、書名、作者、全書開頭 2,000 字。
3. 輸出寫進 `books.genre_profile`：

```json
{
  "primary": "mystery",
  "mixed": [{"genre": "thriller", "score": 0.3, "chapters": [8, 9]}],
  "mechanism_density": {"info_control": 0.62, "threat": 0.18},
  "rationale": "",
  "detected_by": "<model>", "detected_at": ""
}
```

- 題材選項是契約 v2 視角表的 10 種。
- 原型決定（T11）：
  - 實作在 `ingest/s3.py` 的 `run_s3`，入庫圖在 S2 之後跑；每次成功建一筆 `runs`（`ref_id = ingest.s3`），`summary_json` 放完整的密度表（`density`、`strong_share`、章範圍）。
  - 密度的分母＝有 `s1b` 輸出的單位數。`genre_profile.mechanism_density` 一律用程式算的值，不採用 LLM 抄回來的。
  - 10 種題材的 id 在 `domain/genres.py`（registry 沒有題材清單）；7 個機制讀 `registry/perspectives/mechanisms.yaml`。
  - `primary` 不在清單內算驗證失敗（最多試 3 次，仍失敗 job 轉 `error`）；`mixed` 裡不合格的項目只丟該項。429 → `paused_quota`，續跑時只重跑這一步。
  - 全書沒有任何合格訊號時跳過 S3，`genre_profile` 保持空。
  - 改主題材＝`store/books.set_genre_override()`，只寫 `books.genre_override`，不讀原文、不叫 LLM。
  - `signal_tagging` 升到 v2（2026-11-16）：v1 寫「七個機制都要判斷」，模型在每個單位把七個全標一遍，四簽名七個密度全是 1.00。v2 改成只列這段真的出現的機制、明確定義 strong／weak、排除「只是設在過去」與「一般敘述」。四簽名 v2 的密度：info_control 1.00、threat 0.80、language_form 0.74、relations 0.66、journey 0.63、world_rules 0.54、historicity 0.51。所以 §3「七個機制都要判斷」的意思是都要考慮，不是都要輸出。
- 使用者可在 UI 改主題材（`books.genre_override`）。因為 S1 已標所有機制，改完不必重讀全文，只需要對新增的主機制補跑 S4。
- 改主題材後，舊視角已跑的結果卡與證據不刪、不標 superseded；總覽只列新視角的卡，舊的 run 仍可在 run 列表查到（原型決定）。

## 6. S4 深度抽取＋整併（task `deep_extraction`、`consolidation`）

原型只實作**資訊控制機制**（推理的主機制）。

### 誰會被讀

- 有 `info_control` 訊號（weak 或 strong）的單位，都跑機制共用欄位的抽取：`hidden_truth`、`reveal` 的候選。
- 主題材或混入元素含推理時，同一呼叫加上推理擴充提示：`clue_points_to`、`trick`、角色的 `mystery_role／motive／opportunity`。
- 主機制先跑；其他機制的訊號只記錄，原型不深度抽取，但 UI 會列成「也可以問」的推薦（契約 v2「偵測到其他題材的訊號時主動推薦」）。

### S4a 單位抽取

輸入：單位全文、S2 的角色清單（名稱＋id）、該單位的訊號。輸出各類候選，每筆帶 `quote`。這一步不判斷 `is_misdirection`，因為單看一段不知道真相。

### S4b 書層級整併

一次（候選過多時分批，每批 150 筆）LLM 呼叫，**不給全文**，只給所有候選的摘要、章節與引文，加上角色清單：

- 合併指向同一真相的 `hidden_truth` 候選。
- 把 `reveal`、`clue_points_to`、`trick` 連到對應的 `hidden_truth`。
- 依揭曉內容判斷每條線索的 `is_misdirection`；`reader_visible` 取 S4a 的判斷（線索是否在敘述中呈現給讀者）。
- 輸出後依 01 §7 去重，寫入第 1 層。

## 7. 斷點續跑與失敗處理

| 情況 | 處理 |
| --- | --- |
| 伺服器重啟 | `ingest_units` 記每個單位（欄位見 01 §8；`stage`＝`s1a`／`s1b`／`s4a`，`status`＝pending／running／done／failed）。啟動時把殘留 running 的 job 改成 `interrupted`，**不自動續跑**（避免一開機就花額度），使用者按續跑後只跑非 `done` 的單位 |
| 額度用完、429 | 沿用 `core/error_handling.classify_step_failure` 判斷 `rate_limited`；job 轉 `paused_quota`，UI 顯示「可稍後續跑」，不視為失敗。訂閱來源最容易遇到（架構文件「ingest 必須可斷點續跑」） |
| 單一單位反覆失敗 | 重試 3 次後標 `failed`，其餘照跑；完成時列出失敗單位，可單獨重跑 |
| 被 provider 拒絕（blocked） | 不重試（沿用既有 `LLMResponseBlocked` 處理），標 `failed` 並記原因 |
| 換模型重跑第 1 層 | 新 run 取代舊 run；所有下游標「依據已變動」（01 §4） |

原型決定（T08）：

- 「重試 3 次」＝同一個單位一次執行內最多呼叫 3 次；`attempts` 累計所有呼叫次數（含續跑）。
- 429 時該單位退回 `pending`，不佔失敗次數。續跑會跑所有非 `done` 的單位，`failed` 的也會再試。
- `llm_unconfigured` 不是單位的問題：job 直接 `error`（`errorKind: llm_unconfigured`）。
- 啟動時連同 `ingest_units` 殘留的 `running` 一起改回 `pending`。

每個單位的輸出記下 `model`、`prompt_version`，對應契約 v2「每份執行紀錄記下方法論版本、prompt 版本、模型」。

## 8. S5 自動觸發

S4 完成後，依 `genre_profile` 從 registry 取預設方法論（見 03 §4），建立 job 依 DAG 順序執行；上游未跑會自動補跑（一致性規則 7）。結果卡標題取方法論的 `question`。

## 9. 進度回報

沿用既有 murmur 串流的概念：每個單位完成時發一個事件（`stage`、`unit_id`、抽到的角色名或事件標題），給上傳頁的處理動畫用。事件格式見 04。

## 10. Prompt 檔清單
