# 01 證據格式與儲存

補契約 v2 的兩個缺口：每種證據的內容欄位、證據庫怎麼存。範圍是 prototype 縱切片用到的 33 種類型（通用層 22 種、推理 9 種，加上筆記與詮釋），其餘題材之後照同一格式加。

## 1. 儲存決定

| 項目 | 決定 | 依據 |
| --- | --- | --- |
| 證據存法 | 一張外殼表＋每種類型一張內容表，以 `evidence_id` 對接 | 契約 v2 決策 #2 |
| 資料庫 | **單一 SQLite 檔** `var/neo.db`，SQLAlchemy 2（async）＋ aiosqlite | 既有 `DocumentService` 的做法；既有系統九個檔各自管理、刪書要逐一清（見 `docs/guides/data-stores.md`），原型不重蹈 |
| Neo4j | 不用 | 留給資料量大、需要知識圖譜後端時 |
| 向量庫 | 原型不用；`search_evidence` 先用 SQLite FTS5 | 少一個服務；語意搜尋之後再加 |
| 書、章、段 | 沿用既有 `Document / Chapter / Paragraph` 領域模型與欄位（含 `ChapterRole`、`ParagraphRole`） | 既有 `domain/documents.py` |
| 設定 | provider／model／task 與大腦設定存 `var/settings.yaml`，不進資料庫；key 只存環境變數名 | 架構文件「Pipeline 模型配置」 |

## 3. 外殼表 `evidence`

契約的 9 個外殼欄位，加上系統自動補的欄位。**系統欄位不出現在任何寫入工具的參數裡**，由後端推得（架構文件「Agent 無法偽造這些欄位」）。

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `id` | text（uuid） | |
| `book_id` | text | |
| `claim_type` | text | 證據類型，必須在 registry 登錄過 |
| `level` | int | 系統計算：抽取＝1；其他＝`derived_from` 中最高層級＋1 |
| `summary` | text | 一句話摘要，給列表、FTS、agent 讀取時截短用 |
| `discourse_chapter` | int, null | 敘述位置：章（`Chapter.number`）。書層級證據（如 `relation_network`）、筆記、詮釋為 null |

| `known_by` | json, null | `{"reader": bool \| null, "characters": [character_id…]}`，選填 |
| `source` | text | `extraction` / `method` / `user` / `agent` |
| `confidence` | real | 0–1 |
| `review_status` | text | `pending` / `approved` / `modified` / `rejected`（沿用既有 TensionLine 的四態） |

| `basis_changed_at` | datetime, null | |
| `run_id` | text, null | 產生它的 run；使用者詮釋為 null |
| `produced_via` | text | `pipeline` / `ui` / `agent` |
| `agent_backend` | text, null | `deepagents` / `claude-code` / … |

### 引文 `evidence_quote`

| 欄位 | 說明 |
| --- | --- |
| `evidence_id`, `seq` | |
| `paragraph_id`, `start`, `end` | 字元偏移，對齊既有 `ParagraphEntity` 的做法 |
| `text` | 原文片段 |
| `verified` | 由寫入層判定，呼叫端不能自己填（`start`、`end` 也是）。寫入時檢查 `text` 是否為段落原文的子字串（先過既有 `core/utils/text_matching.squash_spacing` 正規化，處理 PDF 字中空白）。找不到 → `false`，證據 `confidence` 乘 0.5 並在 UI 標「引文未對上原文」 |

規則：第 1 層證據至少一段 `verified=true` 的引文，否則不入庫（產品原則「結論必須能回到原文」）。`character` 的抽取輸出沒有 `quote`，它的引文取自 S2 段落標記的首次提及（`ParagraphEntityLinker` 標到的段落與字元偏移，見 02 §4）。第 2 層以上的引文來自上游證據，不另抽。

## 4. 證據層級、取代與「依據已變動」

- **層級**：寫入時由 `evidence_link` 算出，寫入後不變。上游晚寫入（不會發生，因為方法只讀既有證據）不需處理。
- **取代**：`runs` 以 `(book_id, ref_id, scope_key)` 識別「同一個分析」。新 run 成功後，舊 run 的證據 `status=superseded`；被任何筆記引用的 superseded 證據永久保留，其餘可由清理工作刪除。清理時保留的範圍：任何未被取代的證據（含筆記）沿 `derived_from` 往上游走得到的 superseded 證據都留著，讓追溯不會斷（原型決定）。
- **依據已變動**：第 1 層重新抽取、或任一證據被審核為 `rejected` 時，沿 `evidence_link` 反向 BFS，所有下游證據與筆記標 `basis_changed=true`。分析結果之後被重跑時自然取代；筆記不取代，只保留標記。
- **使用者可見**：API 預設只回 `level ≥ 2`；第 1 層只在追溯（`derived_from` 展開）與引文顯示時出現，不能被一般使用者修改（契約 v2 決策 #8）。

## 5. 筆記與詮釋

| 類型 | 層級 | 誰寫 | 內容欄位 |
| --- | --- | --- | --- |
| `note` | 引用證據最高層＋1（引用的證據都 ≥ 2，所以筆記實際 ≥ 3） | 使用者確認後由系統寫入 | `title`、`conclusion`（markdown）、`methodology_run_id`（agent 筆記為 null）、`methodology_trace`（json，形狀見 04 §5.6）、`question`（觸發它的問句） |
| `interpretation` | 引用證據最高層＋1 | 使用者或 agent | `text`。作者記在外殼 `source`（`user` / `agent`），不另設欄位 |

**筆記定義（本次確認）**：筆記＝第 2 層以上、經人審核過的產物。實作上：

- `note` 的 `review_status` 只能是 `approved` 或 `modified`，不存在 pending 的筆記。
- agent 的 `create_note` 一律產生**筆記草稿**（存在 session 裡，不進 `evidence`），使用者在 UI 按確認後才寫入。這比契約 v2「誰決定：使用者，或使用者授權的 agent」更嚴，原型以本次確認為準。
- 筆記引用的證據必須全部 `level ≥ 2`；引用了 `rejected` 的證據不能存。使用者按確認這個動作本身就是審核，不另外要求先確認個別證據。
- 外殼怎麼填：從 UI 的結果卡存的筆記 `source=method`，從 agent 草稿存的 `source=agent`；`summary`＝`title`；`confidence`＝引用證據的最小值；`subjects`＝引用證據 subjects 的聯集。
- 筆記重跑（04 N-06d）的結果是一般的分析結果，只記在該次 job 的結果裡，不寫回筆記；筆記本身不變（原型決定）。

## 6. 內容欄位

共同慣例：

- `*_id` 指向其他證據的 `evidence.id`（角色、事件都是證據）。列表型欄位存 json。
- 枚舉值在 registry 定義，寫入時驗證；LLM 給出不在枚舉內的值時改為 `other` 並保留原字串於 `raw_label`。
- 第 1 層的事件、角色等可被方法「讀」，不可被方法「改」。需要補充第 1 層資訊的方法（如 NS2 算時序）一律產出新證據。
- 欄位的 Python 型別、必填與預設值以 `domain/evidence/<claim_type>.py` 為準（T04 實作時依既有模型補定）。規格沒寫、實作時先定的幾項：
  - 枚舉落在 Pydantic 的 `Literal`；只有清單含 `other` 的枚舉會把未知值改成 `other`，其餘照常驗證失敗。題材擴充欄位的枚舉（`mystery_role`、`case_type`）目前不做這個轉換。
  - 可為 null：`clue_points_to.points_to_truth_id`（誤導線索可能不指向任何真相）、`journey_stage.chapter_start／chapter_end`（`fit=absent` 時沒有章節）、`fairness_gap.reveal_chapter`、`note.question`。
  - `reveal.revealer_id` 目前必填；由敘述者直接向讀者揭曉的情況沒有角色可填，T12 看實際抽取結果再決定要不要放寬。
  - `focalization_pattern.dominant_type` 沿用 `focalization_type` 的三個值；`relation_network.factions[].id` 是該筆證據內的派系代號，不是 evidence id。
  - 以資料當 key 的字典（`chapter_distribution`、`intensity_by_chapter`）key 一律是字串。

## 7. 驗證與去重

- **Pydantic 為準**：每種類型在 `domain/evidence/<claim_type>.py` 有一個 Pydantic model，SQLAlchemy 內容表由它產生或手寫對齊；registry 啟動時檢查兩者欄位一致（仿既有 `tests/docs/test_docs_drift.py` 的思路做成測試）。
- **去重**：契約 v2 規則「類型＋主體＋位置」。作用在同一批待寫入的草稿上（S2、S4b 的最後一步），不和資料庫裡既有的證據比。實作：同 `claim_type`、同 `subjects` 集合、同 `discourse_chapter`，且 `summary` 的字元 3-gram Jaccard ≥ 0.6 → 合併，引文併入，`confidence` 取最大。
- **review**：使用者對第 2 層以上做確認、修改、拒絕；修改後 `review_status=modified`，原值存 `evidence_edits`（仿既有 `TensionLineEdit`），拒絕觸發 §4 的傳播。拒絕可附選填的 `reason`，也存在 `evidence_edits`，用來回頭檢查抽取與方法的品質。
