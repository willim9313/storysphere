# 03 方法宣告

切片內 20 項（18 個方法＋2 個內建方法論 TM3、MY2；通用 15、推理 5）的宣告，以及 registry 的格式與檢查規則。每個方法對照既有 storysphere 的實作，能改寫的就改寫，不從零開始；但**輸出一律改成 01 的證據格式**，既有的 LangGraph／service 程式要改，不是原樣包一層。

## 1. 宣告格式

registry 是四組檔案加兩份清單，啟動時載入並驗證：`registry/claim_types.yaml`（第 1 層證據類型屬於通用層還是哪個題材機制；規則 2、3 與 DAG 的層級都靠它）、`registry/orphans_allowed.yaml`，以及`registry/methods/*.yaml`（方法）、`registry/methodologies/*.yaml`（方法論）、`registry/views/*.yaml`（view 類型目錄，見 05 §4）、`registry/perspectives/*.yaml`（視角：題材的預設結果卡，見 §5）。在契約 v2 範例上補了實作需要的欄位：

```yaml
kind: method
id: info.fair_play_audit        # 穩定 id；API、MCP、trace 都用它
code: MY4                       # 契約編號，給人看
version: 1                      # 改 prompt 或演算法就 +1
layer: genre                    # universal | genre
mechanism: 資訊控制
question: 真相揭曉之前，讀者拿得到足夠的線索嗎？
basis: Knox 1929、Van Dine 1928
grade: 理論                     # 理論 | 技法 | 衍生 | 使用者自建 | 理論＋技法（契約方法目錄的 CH1）
preconditions:
  - exists: hidden_truth
  - exists: reveal
requires:
  - claim_type: hidden_truth
  - claim_type: reveal
  - claim_type: clue_points_to
    genre_ext: mystery
  # optional: true 的輸入有就讀、沒有也照跑，不觸發上游補跑
produces: fairness_gap          # 每個方法只產出一種
scope: per_hidden_truth         # book | per_character | per_character_chapter | per_event | per_hidden_truth | per_motif | per_trick
scope_selector: null            # 選哪些主體，例如 "top_characters(5)"
impl:
  kind: hybrid                  # llm | algorithmic | hybrid
  module: methods/info/fair_play_audit.py
  llm_task: method_strong       # 見架構文件的 task 路由
  prompt: prompts/methods/MY4.md
  config: [config/knox_1929.yaml, config/van_dine_1928.yaml]
view: fairness_matrix
priority: P0                    # P0 原型必做 | P1 可晚點實作
```

方法論：

```yaml
kind: methodology
id: builtin.puzzle_type
code: MY2
version: 1
owner: contract                 # contract | user
question: 這是哪一型的謎題？
grade: 理論
steps:
  - method: info.two_story
  - method: info.trick_class
  - method: info.fair_play_audit
  - synthesis:                  # 內建方法論的最後一步，產出它自己的證據類型
      produces: puzzle_type
      llm_task: method_strong
      prompt: prompts/methods/MY2.md
view: label_card
```

使用者存下的方法論沒有 `synthesis`，產出是筆記（契約 v2「方法論的產出是筆記」）。方法論不宣告 `layer`：步驟裡只要有一個題材方法就算題材層。內建方法論另帶 `basis` 與 `priority`。

視角檔（`registry/perspectives/<genre>.yaml`）的每張卡寫 `ref`（方法或方法論 id）與 `question`（結果卡標題，見 §5）；卡片標題可以和方法自己的 `question` 不同（例：MY4）。

方法的 `question` 規格只給了 11 個；EV2、EV3、CH3、NS1、NS3、TM1、MY3 的問句是 T05 草擬的，YAML 裡標了「草擬，規格未定」，待使用者確認。`scope_selector` 除了 §3 定義的 `top_characters(n)`、`main_motifs(n)`，T05 另用了 `events_with_out_degree(n)`、`characters_with_utterances(n)`、`events_with_tension_signal()` 三個名字，語意照 §4 表格的範圍欄，T13 實作。

## 2. Registry 檢查（啟動時）

契約 v2 的一致性規則，加上實作層的檢查，失敗就拒絕啟動：

1. 每個 `produces` 只能有一個方法產出（同類型不能兩個方法各寫一份）。
2. 每種第 1 層類型至少被一個方法 `requires`，或明列在 `registry/orphans_allowed.yaml`（切片內只有 `book_setting`，理由：讀者在其他題材）。
3. `layer: universal` 的方法不能 requires 任何 `layer: genre` 方法的產出，也不能 requires `genre_ext`（規則 6）。
4. 依 `requires`／`produces` 算出 DAG，不得有環。
5. `produces` 的類型要有 01 的 Pydantic model；`view` 要在 view registry 裡。
6. `requires` 裡 `source: user`／`agent` 的證據只在方法明確宣告 `allow_interpretation: true` 時可讀（規則 4）。

## 3. 執行規則

- **上游補跑**：執行前檢查 `requires`，缺的類型找出產出它的方法先跑（規則 7），不受題材觸發限制。
- **前提條件**：`preconditions` 不成立時不呼叫 LLM，回傳「缺什麼、怎麼補、補了也沒用的情況」（既有產品原則 3「花 token 之前說清楚」）。例：書裡沒有 `hidden_truth` 時，MY4 回「這本書沒有偵測到被隱藏的真相，公平性稽核不適用」。
- **涵蓋率門檻**：輸入不足時不產出退化結果（產品原則 2）。各方法的門檻寫在下表「不產出的條件」。
- **執行紀錄**：每次執行寫一筆 `runs`，記 `ref_id`、`version`、`prompt_version`、模型、參數、輸入證據 id（契約 v2「每份執行紀錄記下…」）。
- **主體選擇**：`top_characters(n)` ＝ `kind=person` 中 `mention_count` 前 n 名（動物與群體不列入）；`main_motifs(n)` ＝ `frequency ≥ 3` 的前 n 個。

### 原型決定（T13 方法引擎）

實作在 `methods/`：`base.py`（介面）、`reader.py`（唯讀查詢）、`selectors.py`、`engine.py`（`MethodEngine.run_method`／`plan_method`）、`jobs.py`（`MethodJobs.trigger_method`）、`s5.py`。

- **方法能讀什麼**：`RunContext.evidence` 只回 `current` 且未被退回的證據，而且只能讀該方法宣告在 `requires`、`preconditions` 裡的類型，讀別的丟 `UndeclaredReadError`。沒有讀原文段落的途徑。讀過的證據 id 記進 `runs.input_evidence_ids`。
- **上游補跑**：必要類型在書裡沒有現行證據時，先跑產出它的方法（遞迴，防循環）；補跑的 run 的 `parent_run_id` 指向這次請求的第一筆 run。缺的是第 1 層類型（入庫才能產出）、或產出者尚未實作、或產出者是方法論時，不補跑，run 標 `not_applicable`。`optional` 的 requires 缺了不補也不擋。
- **一個主體一筆 run**。`scope_key`：`book` 是空字串；其他是 `subject:<證據 id>`，有章時 `subject:<id>|chapter:<n>`。`scope=book` 又有選擇器時只有一筆 run，選中的主體是這筆 run 的焦點，不進 `scope_key`。
- **run 的結果**：前提不成立 → `not_applicable`，`precheck_json` 記 `missing`、`how_to_fix`、`when_useless_even_if_fixed`（snake_case）；沒有符合範圍的主體也是 `not_applicable`。產出 0 筆草稿算 `done`，並取代同一分析的舊結果（輸入不足應該由 `check()` 擋）。失敗 → `failed`，`summary_json.error_kind` 記分類；一筆 run 的寫入在同一交易，失敗時不留半套。
- **寫入前檢查**：草稿的 `claim_type` 必須是宣告的 `produces`；`derived_from` 必須是同一本書的證據、類型在 `requires` 內。違反就整筆 run 失敗。
- **429**：該 run 標 `failed`（`error_kind: rate_limited`），後面的主體不開始，`method_run` job 轉 `paused_quota`。
- **job 去重**：同書、同方法、同參數、同主體清單已有未結束的 `method_run` job 時回傳那個 job（`attached`）。用行程內的鎖，只在單一行程有效。「未結束」含 `paused_quota`、`interrupted`，所以卡住的 job 會一直擋住同一個分析，直到續跑或取消。同一本書有未結束的入庫類 job 時丟 `JobConflictError`（04 §3.3）。job 裡有 run 失敗仍算 `done`，看 `result.failedRunCount`。
- **寫入來源**：`source = method`；`produced_via` 依觸發者：`auto → pipeline`、`user → ui`、`agent → agent`。
- **選擇器的定義**：`top_characters(n)`＝`kind=person` 依 `mention_count` 由多到少（同分看 `first_chapter`）；`main_motifs(n)`＝`frequency ≥ 3` 依 `frequency` 由多到少；`events_with_out_degree(n)`＝現行 `causal_link` 中以該事件為因的不重複果事件數 ≥ n，依 `text_rank`；`characters_with_utterances(n)`＝當發話者的 `utterance` 數 ≥ n，不限 `kind`；`events_with_tension_signal()`＝`tension_signal ≠ none`，依 `text_rank`。`per_character_chapter` 的章＝現行事件出現過的章號。
- **S5**：在入庫 job 之內直接跑（不另建 `method_run` job），run 的 `triggered_by = auto`。先跑通用視角再跑題材視角（`genre_override` 優先，否則 `genre_profile.primary`）；沒有題材時只跑通用視角。尚未實作的方法與方法論的卡跳過，原因記在 `result.s5`。
- **還沒做**：方法論的執行（TM3、MY2）；N-04a 的 `reused`；N-04d 依 `scopeKey` 重跑單一章；宣告裡 `genre_ext`、`requires.source` 的執行語意；`token_usage_json`；SSE 與進度。

### 原型決定（T14：EV2、EV1）

- **共通**：方法裡彼此獨立的 LLM 呼叫用 `methods/universal/_llm.gather_limited` 並行（上限 6），結果順序與依序執行相同；任一呼叫最終失敗整個 run 失敗、不寫半套。解析失敗最多試 3 次；429 不重試直接往外丟。事件給 LLM 時用全書統一的短代號（E1、E2…），不給 UUID。
- **EV2**：依 `(text_rank, id)` 排序，每 30 個一窗、起點相隔 20。每個事件給代號、章、標題、描述、敘事模式、時間提示、後果與第一條引文（最多 300 字）。prompt 列的 `participants` 沒給（EV2 只宣告讀 `event`，讀不到角色名）。不依 `text_rank` 判因果方向（prompt 明說因可以在文本中晚於果）。丟掉：窗外或未知代號、自指、非法 `link_type`。同一對（因→果）跨窗重複時留信心高的，同分取強度高的，再同分取較前面的窗。`derived_from`＝因與果兩個事件。
- **EV1**：圖由現行 `causal_link` 建；有環時依 `(text_rank, id)` 走訪、去掉回邊後算最長鏈（少於 3 個事件不算鏈）。在最長鏈上或出度 ≥ 3 → kernel；出度 0 且入度 ≤ 1 且不在鏈上 → satellite；其餘是邊界，一個事件一次 LLM 呼叫。模型放棄時沿用圖的初判（出度＋入度 ≥ 3 為 kernel），信心 0.4。`derived_from`＝該事件＋與它相連的所有 `causal_link`；**完全孤立的事件因此是第 2 層，不是第 3 層**。這些門檻規格原本沒寫，是實作時訂的。
- **四簽名的結果與已知問題**：EV2 產出 402 條連結；EV1 判 309 個 kernel、122 個 satellite（72% 是 kernel），沒有鑑別力。最長鏈 39 個事件全在第 10–12 章（事件抽得細，連續動作串成長鏈），鏈上有瑣碎事件也被判 kernel；278 個邊界事件裡 LLM 把約 257 個判成 kernel。門檻與 prompt 待調。

| 推理 | 誰在什麼時候知道什麼？ | CH5 |
| 推理（也可以問） | 這是哪一型的謎題？ | MY2 |

「也可以問」清單＝ registry 裡所有 `question`，扣掉已自動跑的。使用者提問路徑（契約 v2 路徑二）先比對這張清單，比不到才交給 agent 臨時組合。

其他題材訊號的推薦：`registry/perspectives/mechanisms.yaml` 列出七個機制給使用者的問題（取自契約 v2「七個題材機制與方法」表的「給使用者的問題」欄），加 `supported: true／false`。原型只有資訊控制是 true，其餘在總覽顯示為「尚未支援」。

## 6. 每個方法的模組介面

所有方法實作同一個介面，讓 UI 按鈕、agent 的 `run_method`、方法論步驟走同一條路（架構文件「結果完全一致」）：

```python
class Method(Protocol):
    decl: MethodDecl                                    # 從 YAML 載入

    async def plan(self, ctx: RunContext) -> list[ScopeItem]:
        """依 scope／scope_selector 決定要跑哪些主體；不叫 LLM。"""

    async def check(self, ctx: RunContext, item: ScopeItem) -> Precheck:
        """前提條件與涵蓋率；不成立時回原因，不叫 LLM。"""

    async def run(self, ctx: RunContext, item: ScopeItem) -> list[EvidenceDraft]:
        """讀證據庫、產出草稿；不直接寫資料庫。"""
```

`EvidenceDraft` 只有內容欄位、`summary`、`derived_from` 與 `confidence`；層級、來源、run、模型等系統欄位由寫入層補上（01 §3）。方法只讀證據庫，**不讀原文段落**——需要原文的只有入庫（契約 v2「兩條路徑都只讀證據庫，不重讀文本」）。原文引文透過上游證據的 `evidence_quote` 取得。
