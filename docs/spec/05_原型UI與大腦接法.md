# 05 原型 UI 與大腦接法

## 1. 目的與範圍

原型 UI 是**檢視器**：看新版後端的產出是否符合契約，並能接上 agent 大腦做提問。不是新版正式前端，也不搬既有九個書籍頁。

成功條件：

1. 用 `storysphere_benchmark` 的推理文本（`01_推理_四簽名`）跑完入庫，UI 能看到每個步驟的產出與失敗單位。
2. 自動觸發的 10 張結果卡都能打開、看到 view、展開證據、追溯到原文。
3. 同一個問題分別用 deepagents（Gemini）與 Claude Code 回答，都能產生筆記草稿、確認後存成筆記，且筆記能重跑（架構文件階段二的通過條件，原型提前驗證）。

原型決定：

- 介面只做繁體中文（既有產品要求中英並重，原型先不做 i18n）。
- 桌面寬度 ≥ 1024px；不做窄版。
- **開發者檢視**：設定頁有開關，打開後可看第 1 層證據與原始 trace。契約 v2 規定一般使用者看不到第 1 層，原型要驗證抽取品質，所以預設打開，正式版關掉。

### 3.3 Agent 工作區

左邊是對話，右邊是「本次分析結果」工作檯：每個問題的答案直接以完整的結果呈現，使用者逐一決定要不要留。

```
┌ 大腦：[deepagents · gemini-2.5-flash ▾]  session 8c1e  L0  [新對話] ────────────┐
├─────────────────────┬──────────────────────────────────────────────────────────┤
│ 對話                 │ 本次分析結果 · 3 個 · 未儲存 2     [全部｜未儲存｜已儲存] │
│ 你：華生知道真相的…  │ ┌ 結果 A · 未儲存 · L3 · 臨時組合 CH5＋MY1 ───────────┐ │
│ › run_method CH5     │ │ 誰知道同伴的來歷？  [存成筆記][另存方法論][捨棄]   │ │
│ 大腦：讀者早兩章……   │ │ [view：knowledge_matrix]  │ 結論（可改）           │ │
│ [→ 結果 A]           │ │                           │ 引用的證據 · 6         │ │
│ 你：那讀者被誤導到…  │ │ 怎麼得出的：run_method → get_run → show_view [重跑]│ │
│ [→ 結果 B]           │ └──────────────────────────────────────────────────┘ │
│ ┌ 寫入確認 ────────┐ │ ┌ 結果 B · 未儲存 … （同上結構）─────────────────────┐ │
│ │ 允許／拒絕       │ │ └──────────────────────────────────────────────────┘ │
│ └─────────────────┘ │ ▸ 結果 C · 已存成筆記 · 線索公平嗎？   在筆記中開啟    │
│ [輸入問題……][送出]   │                                                        │
└─────────────────────┴──────────────────────────────────────────────────────────┘
```

- **一個問題＝一個結果**：同一輪（`turnId`）的 `show_view` 與 `create_note` 草稿，在右側組成一個結果：view、可改的結論、引用的證據、怎麼得出的（該輪的工具呼叫）。對話裡只留旁白與「→ 結果 A」的連結。
- **使用者決定去留**：每個結果有三個動作。
  - **存成筆記**：走 N-06c（`origin=draft`），按下即人工審核（01 §5）。
  - **另存方法論**：把這一輪的工具呼叫順序存成使用者方法論（N-07e，`fromSession`）；與存成筆記是兩件事，可以都做。
  - **捨棄**：草稿標 `discarded`（N-10k）。
- **沒存的結果**：只是一次分析結果，下次重跑同一個分析就被取代；畫面上明寫這點。已存的收合成一行，連到筆記。
- **取用既有結果**：大腦可以用 `get_run` 拿已跑過的結果卡，結果上標「取用結果卡 MY5」，不重跑、不花 token。
- 工具呼叫在對話中只顯示一行摘要；完整參數與回傳在開發者檢視的 trace。
- 大腦的文字只是旁白；結果的 view 與草稿都來自它寫進系統的 records（架構文件原則 3）。

原型決定（T27，2026-11-17）：

- **畫面狀態從 REST 重建**：對話（N-10c）、工具呼叫與 view（N-10i 的 `show_view` 參數）、草稿（N-10j，依 `turnId`；T27 之前的草稿用 `question` 對回那一輪）。SSE 只即時接 `text_delta`，其他事件收到就重抓，所以重新整理或打開舊 session 畫面都一樣。
- **只有 view、沒有草稿的結果**：不能存成筆記、也不能捨棄（兩個動作都作用在草稿上）；卡上說明可以請大腦「整理成筆記」。
- **另存方法論**照 04 N-07e 只取該輪的 `run_method`；沒有就停用並寫明原因（大腦取用現成結果時多半如此）。
- **已關閉的 session 唯讀**：可以看結果，不能送訊息或存；關閉時 `open` 的草稿已被標 `discarded`。
- **不做**：「怎麼得出的」旁的「重跑」（存成筆記後用筆記的重跑）；結果卡上的層級標示（草稿還沒有層級）。
- 結論裡不在引用清單的 id（大腦抄錯）只在卡上警示，不擋儲存；結論可以在存之前修改。

## 4. View 目錄（`show_view` 的類型）

方法宣告的 `view` 與 agent 的 `show_view(view_type, data_ref)` 共用這張表。`data_ref` 是一個 run id 或一組 evidence id；view 自己向後端取資料，agent 不傳資料本體，也不寫 UI。

| view_type | 用在 | 呈現 |
| --- | --- | --- |
| `causal_graph` | EV2、EV1、EV3 | 事件 DAG，kernel 粗框、satellite 細框，依 `text_rank` 由左到右 |
| `character_arc` | CH2 | 每個角色一條章節橫軸，分段標 phase |
| `network` | CH4 | 力導向圖，依派系群聚；沿用既有圖譜頁的群聚手法 |
| `timeline_dual` | NS2、MY1 | 上下兩軌：敘述順序與故事順序（MY1 換成「犯罪的故事」與「調查的故事」），連線表示對應 |
| `tension_lines` | TM1、TM2 | 每條張力線一列，章節上的強度 |
| `theme_card` | TM3 | 主題命題、Frye mythos、Booker plot、支撐的張力線 |
| `symbol_trend` | SY1 | 意象的章節分布與意涵轉變 |
| `knowledge_matrix` | CH5 | 角色 × 章節：已知、未知、錯誤認知 |
| `fairness_matrix` | MY4 | 真相 × 章節：線索出現、是否讀者可見、是否誤導、揭曉點 |
| `suspect_matrix` | MY5 | 嫌疑人 × 線索熱圖＋逐章嫌疑分數折線 |
| `stage_strip` | NS1 | 12 階段沿章節排列，標 fit 強弱 |
| `label_card` | CH1、CH3、MY3、MY2 | 分類結果＋理由＋依據等級 |
| `evidence_list` | 任何類型 | 通用：證據列表＋引文，任何沒有專屬 view 的類型都能用 |

### 4.1 各 view 的資料與畫法（原型決定，2026-11-17，T22）

範圍調整後先做有資料的 5 種；`fairness_matrix` 等 MY4 做完再補，`timeline_dual`、`suspect_matrix` 的方法不做（STATUS）。

`fairness_matrix`（T18 MY4 之後補上，2026-11-17）：列＝每筆 `fairness_gap`（判定徽章＋真相敘述），欄＝正文章（`role=body`）。格內是指向該真相的 `clue_points_to`：實心＝讀者可見、空心＝看不到、菱形＝誤導；揭曉章加框標「揭」，揭曉前的格子加底色、揭曉後的線索淡化。點一列在側欄看判定、揭曉前的數字、違反的規則、`gap_description` 與揭曉前的線索。真相敘述與線索都是第 1 層，view 直接以 `includeL1` 取。

**取資料的原則**：view 依「這個分析產出的證據類型」取本書所有 current 證據（N-05a `claimType=`，第 1 層要帶 `includeL1=true`），不是只取結果卡的那一個 run。原因：CH2、CH5 每個角色（CH5 還每一章）各一筆 run，結果卡的 `runId` 只是最新的一筆。agent 的 `show_view` 給 `evidenceIds` 時，只畫那些證據（N-04e）。

| view_type | 取的證據 | 畫法 | 點一下 |
| --- | --- | --- | --- |
| `evidence_list` | run 的 `primary`（N-04e）或指定的 id | 每筆一列：類型、層級、摘要、第一段引文、章 | 打開證據（詳情頁右欄） |
| `knowledge_matrix` | `belief_state`＋其 `character_id` 的 `character` | 列＝角色，欄＝章；格子深淺＝到該章已知事件數／全部事件數；有錯誤認知的格子加標記 | 側邊列出該角色到該章的錯誤認知（belief、truth、來源事件） |
| `character_arc` | `arc_segment`＋`character` | 每個角色一列章節橫軸；每段一個色塊（`chapter_start`–`chapter_end`），標 `phase` | 顯示該段 `description` |
| `causal_graph` | `event`（第 1 層）＋`causal_link`＋`event_role` | 事件為節點，x＝章、同章依 `text_rank` 排；`causal_link` 為有向邊，粗細依 `strength`；有 `event_role` 時 kernel 粗框、satellite 細框，可只看 kernel | 顯示事件標題、描述與角色理由 |
| `network` | `relation_network`（書層級一筆）＋`character` | 角色為節點，依 `factions` 群聚（compound node），大小依 `centrality`；派系之間的邊依 `inter_faction` 的 `cooperation`（實線）／`rivalry`（虛線） | 顯示角色名稱、派系、中心度 |

## 5. 大腦接法

三種設定，都走同一個 Agent Gateway 介面（架構文件的 `AgentBackend` Protocol），UI 只在大腦選單切換。

| 選項 | 適合 | 需要 | 原型優先 |
| --- | --- | --- | --- |
| 無大腦 | 只看自動結果卡、從「也可以問」點分析 | 只需 pipeline 模型（Gemini API key） | 必做 |
| deepagents ＋ Gemini | 預設大腦 | 同上；大腦模型可另設 | 必做 |
| Claude Code（ACP） | 使用者已有 Claude Code 訂閱 | 本機已安裝並登入 Claude Code、Node | 必做（架構文件原排在階段二，原型提前） |

Pipeline（入庫與方法）一律用 provider 設定，不經大腦；原型最少只設 Gemini。

### 5.1 deepagents

- 用 `deepagents.create_deep_agent(model=..., tools=..., system_prompt=..., skills=[...])`。
- MCP 工具：Gateway 用 `mcp` 2.x 的 `Client` 經 HTTP、帶本 session 的 token 連 StorySphere 自己的 MCP server，`list_tools` 後依白名單包成 LangChain 工具傳進 `tools`（`gateway/mcp_tools.py`）。不用 `langchain-mcp-adapters`：它要求 `mcp<2`，與 MCP server 衝突（T25 使用者決定）。
- Skills 傳 session 工作目錄下的 skills 資料夾，由 Gateway 依題材挑選後複製進去。
- 權限 L0（架構文件）：deepagents 自帶的檔案工具只碰虛擬檔案系統；關掉 shell 類工具。原型做法（T25）：檔案 backend 以 session 工作目錄為虛擬根、寫入一律拒絕；`execute`、`write_file`、`edit_file`、`task`（子 agent）對模型隱藏，硬叫回錯誤；只留 `ls`／`read_file`／`glob`／`grep` 讀 skills。
- 大腦模型：LLM task `brain`（N-08a）；deepagents 要 `bind_tools`，所以取第一個可用模型、不包備援鏈。
- 串流用 LangGraph 的 `astream_events`，Gateway 轉成 AgentEvent。

### 5.2 Claude Code（ACP）

- Gateway 以子 process 啟動 `npx -y @agentclientprotocol/claude-agent-acp`，Python 端用官方 `agent-client-protocol` SDK（`spawn_agent_process`）當 client。
- 建 session 時傳入 StorySphere MCP server（HTTP，帶本 session 的 token）。
- Skills 經 ACP 建 session 時一起帶：在 session 目錄建一個本機 plugin（`plugin/.claude-plugin/plugin.json`＋`plugin/skills/<name>/SKILL.md`），以 `_meta.claudeCode.options.plugins: [{type: "local", path}]` 傳入，大腦看到的是 `storysphere:<name>`（T26 實測，使用者決定）。ACP 協定本身沒有傳 skill 的欄位；放 `.claude/skills/` 要打開 `settingSources: ["project"]` 才會載入，會連帶讀進上層目錄的 `CLAUDE.md`。
- Claude Code 的 session 目錄放系統暫存目錄（repo 外）：在 repo 裡時，Claude Code 會往上讀 repo 的 `CLAUDE.md`，並依 git repo 帶進本機的 auto-memory。子 process 另設 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`，環境變數只給白名單（`HOME`、`PATH` 等），不傳後端金鑰。
- 關掉 Claude Code 自帶的 Bash、寫檔、抓網頁工具；ACP 的 permission request 一律轉成 UI 的確認事件。adapter 的預設值做不到這點，建 session 時必須明確設以下四項（T02 spike 實測，見 `docs/plans/20261115-acp-spike.md`）：
  - `_meta.claudeCode.options.tools: ["Skill"]`：內建工具只留讀 skill 的 `Skill`（用白名單，不用黑名單；`[]` 會連 skill 都看不到，T26 實測）。
  - `_meta.claudeCode.options.settingSources: []`：不載入使用者與專案的 Claude 設定（允許規則、預設權限模式、MCP server）。
  - `_meta.claudeCode.options.extraArgs: {"strict-mcp-config": null}`：只留 session 傳入的 MCP server，不帶帳號的連接器。
  - 建好 session 後立刻 `set_session_mode("default")`：adapter 預設選 `auto` 模式，不會逐次送 permission request。
- MCP 工具呼叫也會觸發 permission request。Gateway 依工具名分流：白名單內的讀取與分析工具回 `allow_once`；需要使用者確認的轉成 `approval_request`；其餘拒絕。不回 `allow_always`。
- 權限分流（T26）：`mcp__storysphere__<L0 工具>` 與 `Skill` 回 `allow_once`（`add_interpretation` 的確認由 MCP server 自己發，不重複問）；其餘拒絕並記 `trace_calls.status=denied`。大腦若把權限模式切離 `default`，Gateway 收到 `current_mode_update` 就切回去。CLI 內建 skill（code-review 等）仍會出現在清單裡，但大腦沒有可用的工具，做不了事。
- 使用者用官方流程登入，StorySphere 不碰憑證（架構文件的條款段落）。
- **開工前的 spike（已完成，2026-11-15 通過）**：用最小 MCP server 確認 Python ACP client 能啟動 adapter、傳入 MCP、收到工具呼叫事件。備案（改用 Claude Agent SDK 做 vendor SDK adapter）不需啟用。
